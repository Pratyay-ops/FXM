# @fxm/desktop

The FXM desktop app for macOS, Windows and Linux: the web app (`apps/web`) in a [Tauri 2](https://v2.tauri.app) shell. This is FXM's installable "applet". It reaches YouTube, Spotify and every other service through native networking in Rust (tauri-plugin-http), so it needs no FXM Connect extension. Stage 7.1 built the shell, stage 7.2 its networking, stage 7.3 its playback and OS integration (a tray menu, a close button that keeps the music playing, playback in a hidden window and the system media controls) and stage 7.5 its [releases](#releases) and [updates](#updates). How users install it is in [INSTALL.md](INSTALL.md).

Setup, prerequisites per OS, commands and disk usage are in [DEVELOPMENT.md → Desktop app](../../docs/DEVELOPMENT.md#desktop-app). In short:

```sh
make desktop-setup   # pinned Rust into .tools/, plus dependencies
make desktop-dev     # web dev server on port 5260 + the app window, with hot reload
make desktop-build   # FXM.app on macOS (all bundle types elsewhere), in src-tauri/target/release/bundle/
make desktop-check   # rustfmt, clippy, cargo test
scripts/run.sh pnpm --filter @fxm/desktop smoke   # the live smoke test, in a hidden window
scripts/run.sh gh workflow run desktop.yml --ref <branch> -f release-dry-run=true   # the release builds, as a dry run
```

## How it works

- **Frontend.** `tauri build` runs `pnpm --filter @fxm/web build:desktop`, which builds the web app with base `/` into `apps/web/dist-desktop`. Tauri embeds that folder in the executable and serves it from `tauri://localhost` (`http://tauri.localhost` on Windows). The router takes its basename from `import.meta.env.BASE_URL`, so nothing in the web app changes. Unknown paths fall back to `index.html`, so reloading a deep link works.
- **Development.** `make desktop-dev` starts Vite with `--base=/ --port 5260 --strictPort` and points the window at `http://localhost:5260`. Release-only behaviour, the CSP in particular, needs `make desktop-build`.
- **Window.** One window labelled `main`: 1200×800, at least 360×600, titled FXM, with the dark theme's background (`#0b0b0f`) until the page paints. tauri-plugin-window-state restores its size, position, maximized and full-screen state, but never starts it hidden. tauri-plugin-single-instance brings it to the front when FXM is launched a second time, also when it was hidden in the tray. Its close button may hide it instead of quitting, and its page keeps running while hidden: see [Playback and OS integration](#playback-and-os-integration). `dragDropEnabled: false` leaves drag and drop to the page, as in a browser: Tauri's native file-drop handling would turn off HTML5 drag and drop on Windows, which playlist reordering may rely on.
- **Links.** tauri-plugin-opener opens `target="_blank"` links in the default browser.
- **Network.** Every request the web app makes through `ctx.fetch` goes through Rust, and IPC messages pass the isolation hook first: see [Network](#network) below, which also says where they don't.
- **Playback.** `<audio>` in the webview, as on the web, with the desktop app's rules, a tray menu and background playback: see [Playback and OS integration](#playback-and-os-integration).
- **Version.** The app's version is `apps/desktop/package.json`'s (`"version": "../package.json"` in `tauri.conf.json`), which `make release-pr` sets with every other package's.
- **Releases and updates.** Every release builds the installers for each platform, the updater's files and `latest.json`, and the app installs newer versions after asking: see [Releases](#releases) and [Updates](#updates).
- **The isolated evaluator** (stage 1.11, `src/evaluator.rs`). The app's `fxm-evaluator` plugin opens a hidden webview window on its own URI scheme, `fxm-eval://localhost/eval.html` (`http://fxm-eval.localhost/` on Windows), and serves `apps/web/sandbox/eval.html` from it with that document's own policy: its inline script by hash, `'unsafe-eval'`, and no connections. The main window drives it through the plugin's `open` (a new window each time), `eval` (`eval_with_callback`) and `close` commands, which `fxm-evaluator:default` in `capabilities/default.json` grants to the main window only. YouTube's player script runs there, never in the main window ([packages/platform/src/evaluator/README.md](../../packages/platform/src/evaluator/README.md)). What its page can't do:
  - **Call commands.** No capability names its webview, so it can call no plugin command, and none of the app's own commands either: Tauri checks app commands (those of `tauri::Builder::invoke_handler`) against the capabilities only when the app declares an access-control manifest, and `build.rs` declares one for them (see [App commands and permissions](#network)). Without it, any page at a local URL, the evaluator's included, could call them; `test/evaluator.test.ts` fails if an app command is registered while `build.rs` declares no `app_manifest` for it.
  - **Leave its document.** The window refuses every navigation away from `eval.html` and every new window, and `eval` destroys a window that shows anything else instead of reading it. On macOS and Linux one page gets through before the plugin's guard sees it: Tauri always lets a webview load its isolation frame's page (stage 7.2), a local page that may connect nowhere.
  - **Keep the app running.** Tauri quits once no window is left, hidden ones included, so the plugin destroys the evaluator window when the main window is destroyed. Since stage 7.3 the close button hides the main window wherever the Dock or a tray icon can bring it back; where it closes it (Linux without a tray icon), FXM still quits, and Quit ends FXM whatever windows are open.
- **The evaluator while FXM is hidden.** Its window is never shown, and WebKit stops a hidden page's timers (macOS), as the smoke test's hidden window found, so it gets `backgroundThrottling` disabled like the main window (stage 7.3): the player resolves its next track while FXM is hidden too. Windows and Linux have no such switch.
- **The evaluator and the isolation hook.** The main window's calls to the plugin pass the isolation hook like any other IPC message, and reach Rust unchanged (`test/isolation.test.ts`). The evaluator's page needs no IPC, since the main window reads it with `eval`, and its policy keeps out the isolation frame that Tauri adds to every page.
- **Still to check in a running app** (stage 1.11): that Tauri serves the `fxm-eval:` responses as the plugin writes them, policy included; that the navigation guard holds; that the evaluator document runs although its policy blocks the isolation frame, and keeps answering while FXM is hidden (WebView2 and WebKitGTK may throttle it, which the main window's Web Lock doesn't cover); and that FXM quits with the evaluator window open, through Quit on macOS, Windows and Linux, and through the close button where it closes the main window (Linux without a tray icon).

The tests in `test/` pin the CSP, the isolation pattern and its hook, the http plugin's scope and settings, the permissions around them, `default.json` as the only capability file, the app's commands, the plugins `src/lib.rs` registers, the app's own evaluator plugin included, the tray feature, the window's background throttling, and the updater's endpoint and settings, so widening any of them is always a deliberate change.

## Network

The web app never uses the webview's own `fetch` here. In the desktop app, `createPlatform()` from `@fxm/platform` sees Tauri's runtime and sends every provider request through `createDesktopFetch()` ([`packages/platform/src/desktop.ts`](../../packages/platform/src/desktop.ts)), which hands it to tauri-plugin-http in Rust. From the webview, a request would carry the app's own origin, which InnerTube refuses with 403 (`tauri://localhost` on macOS and Linux, `http(s)://tauri.localhost` on Windows, the dev server's under `make desktop-dev`), and the webview's cookies.

**Headers.** The policy is the native transport's (`NATIVE_ORIGINS` in [`packages/platform/src/native.ts`](../../packages/platform/src/native.ts)), and `createDesktopFetch()` enforces it once more at the last step:

| Requests to | `Origin` | `User-Agent`, unless the request names one |
|---|---|---|
| YouTube: InnerTube, `sw.js_data`, the player JavaScript, googlevideo, and its image servers `i.ytimg.com` and `*.ggpht.com` | None | The webview's own, which is a browser's: WebView2's, WebKitGTK's, or on macOS WKWebView's completed to Safari's |
| Spotify's API hosts | `https://open.spotify.com` | The same browser agent |
| Spotify's image server `i.scdn.co`, and Last.fm's web player (`www.last.fm/player/station/`) | None | The same browser agent |
| Services that ask apps to name themselves: MusicBrainz, Cover Art Archive, ListenBrainz, the Last.fm API, LRCLIB, Internet Archive, Jamendo, iTunes Search, SponsorBlock | None | FXM's: `FXM ( https://github.com/Pratyay-ops/FXM )`, as MusicBrainz asks |

- The agent goes by who runs the host (`sendsBrowserAgent`): Google and Spotify never see FXM's own agent, which would single out the same address's traffic that otherwise reads as a browser's, and give them an easy string to block. On the web, those requests carry the browser's own agent.
- Headers travel only in `init.headers`, as a plain object: the plugin reads forbidden headers such as `Origin` only from there, and a `Request` object's headers would lose them.
- The `Origin` comes only from the transport's `init.origin`, never from the headers. "None" (`null`) goes to the plugin as `origin: ''`, which the plugin removes. That takes the `unsafe-headers` feature: without it the plugin always adds the webview's origin. A non-`https:` origin is turned into none too, so no request can ever carry the webview's.
- The plugin's own agent, `tauri-plugin-http/<version>`, never goes out: Spotify refuses it, and it would single out FXM's traffic. Neither does a `Cookie` or `Host` header.
- InnerTube calls keep the CORS-simple shape of every platform and draw from the request budget, with `visitorData` in the request body. The session's visitorData is server-issued: native requests can read `https://www.youtube.com/sw.js_data`, which the YouTube provider (stage 1.3) takes it from.
- Responses arrive compressed, as in a browser: the plugin is built with `gzip` and `brotli`, so InnerTube's and Spotify's JSON, often hundreds of KB, crosses the network several times smaller. A request with a `Range` header asks for `identity`, so media probes and downloads stay byte for byte.
- Errors follow `fetch`, for the response and for reading its body, and refusals by FXM's rules are `TransportError`s, as on every platform. Their messages name a URL only by its scheme, host and path: a googlevideo URL's query carries the user's IP address and signatures.

**Scope.** `capabilities/default.json` lets the plugin reach exactly the hosts in the platform's host table (`HOST_RULES` in [`packages/platform/src/hosts.ts`](../../packages/platform/src/hosts.ts)), HTTPS only, and Last.fm only under `/player/station/`. The test builds the expected list from the table, so a host added there fails it until it is added here too. One row stays out on purpose, and the test names it: BotGuard's interpreter (`www.google.com/js/th/`, stage 1.11). Only the PO-token rungs fetch it, and they need an evaluator document at YouTube's origin, which this app's isn't, so the app never asks for it. `createDesktopFetch()` asks the plugin to follow no redirect (`maxRedirections: 0`): the transport follows each hop itself and checks it against the host table first, so a redirect out of the table, or to a host of another class, fails (a `TransportError`, `redirect`). googlevideo's redirects to other `*.googlevideo.com` hosts and Internet Archive's to its storage hosts, such as `dn710102.ca.archive.org`, stay inside. `scopeRedirects` in `tauri.conf.json` still checks every redirect the plugin follows against its scope, for page script that calls the plugin through the IPC itself. FXM's own site is not in the table yet, so `createDesktopFetch()` sends it to `user_host_fetch`, which refuses it: the signed updates of stage 1.13 (`https://fxmusic.pages.dev/updates/`, see [packages/platform/src/updates](../../packages/platform/src/updates/README.md)) need that folder in the scope, and `createDesktopFetch()` sending it through the plugin, before the updater is wired into the app.

**No cookie jar.** The plugin's default `cookies` feature is off. It would save every response cookie in plain text in `.cookies` in the app's cache folder and send it back with later requests. FXM never sends a `Cookie` header from the web app, and `Set-Cookie` never reaches page JavaScript. Stage 7.4 decides how Spotify credentials are stored.

**The isolation hook.** `createDesktopFetch()` binds only the requests made through it, but page script can call the HTTP plugin through Tauri's IPC directly. So the app uses Tauri's [isolation pattern](https://v2.tauri.app/concept/inter-process-communication/isolation/) (`app.security.pattern` in `tauri.conf.json`, and the `isolation` feature of `tauri` and `tauri-build`). Tauri's IPC hands each message from a page to [`isolation/hook.js`](isolation/hook.js), in a sandboxed iframe of its own origin, which encrypts the payload the hook returns with a key only that frame has. Rust decrypts every payload with that key and refuses one it can't, so each payload Rust reads has passed the hook, with the two exceptions below.

Only the payload is encrypted. The command and the payload's content type travel in the clear, next to it, so page script can resend an encrypted payload under another command, or have bytes read as JSON. The hook therefore treats every message as a request to the HTTP plugin (`plugin:http|fetch`), whatever its command:

- A payload that Tauri sends as bytes (an array, an `ArrayBuffer`, a typed array or a `DataView`) is replaced with one the plugin refuses: the bytes could hold any JSON. No FXM command takes bytes.
- Any other payload is first converted the way Tauri's serializer converts it after the hook (a `Map` becomes an object, a `Uint8Array` or an `ArrayBuffer` an array of numbers), so the rules apply to exactly the JSON Rust reads. A payload Tauri couldn't send (a cycle, a `BigInt`) is refused, so the call fails instead of never answering.
- A `clientConfig` (the plugin's request) that isn't an object is refused: serde also reads the request from an array, field by field, `proxy` included. From an object the hook keeps only the fields FXM sends: method, URL, headers, body, `maxRedirections` and `connectTimeout`. So it drops the plugin's per-request `proxy` option, which no scope or setting restricts. With it, page script could make Rust open a TCP connection to any address and port, the user's own network included, read from the errors whether the port is open, send a `CONNECT` line with a `Proxy-Authorization` of its choosing, or look up a proxy host name made of data. It also drops `danger` (TLS exceptions), which the plugin refuses anyway without its `dangerous-settings` feature, and any option a later plugin release adds.
- The headers lose `Cookie`, `Cookie2`, `Host` and `Proxy-*`, and get exactly one `Origin`: the `https:` origin of a real site, else none, never the webview's own.

FXM's own messages reach Rust byte for byte as they would without the hook. The two exceptions:

- **No payload.** A request without a payload skips decryption, but it gives a command no arguments, so it can't carry a request for the plugin.
- **The start-up gap.** Tauri's own script comes first in the frame's page and handles messages as soon as it has imported its key, and `hook.js` is the next script. A message that reaches the frame while the browser pauses between those two scripts, as a browser may when parsing runs long, skips the hook, and page script can reload the frame to try for that pause again. An initialization script for every frame (Tauri's `js_init_script_on_all_frames`) runs before any script of a page, so it could set the hook first and close the gap. That is still to do, and it is now due: stage 1.13 has added `blob:` to `script-src`, so signed modules run in this webview while the gap is open (see [What page script can reach](#what-page-script-can-reach)).

`test/isolation.test.ts` runs the hook as the frame does, with a copy of Tauri's serializer, on FXM's own messages and on every way found to get a proxy or a forbidden header through: a `Map` payload or request, another command's payload, bytes labelled JSON, a request read by position, `String` objects. It runs the hook on the same origins as `createDesktopFetch()`'s rule too. The live smoke test calls the plugin through the IPC with a proxy nothing answers at, and checks that the host answers. A Rust test checks that the built app uses the pattern: without the crate feature, Tauri would quietly ignore it. Each IPC call costs one more `postMessage`, a JSON round trip and an AES-GCM encryption.

**Hosts the user adds.** Tauri can't change a plugin's scope at runtime, so hosts typed into Settings, such as an Invidious instance or a Spotify secret source, go through the app's own commands in `src/user_hosts.rs`:

| Command | What it does |
|---|---|
| `user_hosts` | Lists the approved hosts |
| `approve_user_host` | Asks the user, in a native dialog over the main window, whether FXM may contact the host. Only a public domain name, with an optional port, can be approved: no IP address, no single-label name, no `.local`, `.lan`, `.internal` and the like. Errors: `invalid-host`, `not-focused`, `busy`, `too-soon`, `refused`, `dialog`, `storage` |
| `revoke_user_host` | Removes a host |
| `user_host_fetch` | Fetches from an approved host. Errors: `bad-request`, `not-approved`, `forbidden-address`, `proxy-configured`, `too-large`, `network` |

- Only the user can grow the list, by choosing "Allow" in the dialog: page script, a resolver module included, can read and shrink it but never add to it, so it can't make `user_host_fetch` reach a host the user didn't approve. That binds this command only: see [What page script can reach](#what-page-script-can-reach).
- The dialog shows only while FXM's window is visible, not minimized and focused (`not-focused` otherwise): the command never brings the window forward, so a script can't pull FXM in front of another app, or raise the question just as the user presses Return in FXM's search box. On macOS and Windows "Don't Allow" is the default button, which Return presses. GTK (Linux) reports closing the dialog and its second button alike, so there "Allow" is its OK button. Either way only a click on "Allow" approves. One question at a time (`busy`), the next only 10 s after the last answer (`too-soon`), and none about a host the user refused until FXM restarts (`refused`).
- The dialog comes from [rfd](https://github.com/PolyMeilie/rfd) directly. tauri-plugin-dialog, which wraps it, would inject a script into every page that replaces `window.alert` and `window.confirm` with IPC calls the app doesn't allow: `alert()` would show nothing, and `confirm()` would return a Promise, which is always truthy, so `if (confirm('Delete?'))` would go ahead without asking.
- `user_host_fetch` sends `GET` and `HEAD` only, over HTTPS, without cookies, credentials or any header from the page, with FXM's User-Agent. Names must resolve to public internet addresses: loopback, private, link-local, shared and other special-purpose addresses are dropped after DNS resolution, so an approved name can't point the command into the user's network. No redirects: the command hands a redirect back as it is, and the transport follows it to the same host only, through the command again. At most 8 MiB in 30 s, counted on the body actually read (a `HEAD` response has none, whatever its `Content-Length`). `Set-Cookie` is dropped, and header values reach the page one character per byte, as browsers expose them, so a UTF-8 file name can't break the response.
- **Never through a proxy.** The HTTP plugin follows the system's and the environment's proxy settings (`system-proxy`), but `user_host_fetch` connects directly: its public-address check has to see the address it connects to. So while a proxy is set for a host, the command refuses it (`proxy-configured`) rather than reveal the user's own address to it, which a user who set a proxy to hide that address wouldn't expect. Settings should say so next to the hosts.
- Messages name a host or an origin, never a URL's path or query.
- The list lives in `user-hosts.json` in the app's config folder (on macOS, `~/Library/Application Support/io.github.pratyayops.fxm/`).
- In the web app, `createDesktopUserHosts()` from `@fxm/platform` wraps the commands. Pass `userHosts: () => hosts.current()` to `createPlatform()`, so the transport routes those hosts; Rust checks them again on every request.

**App commands and permissions.** `build.rs` lists the app's commands in an app manifest, which gives each an `allow-…` permission and makes Tauri check app commands against the capabilities, as it does plugin commands. Without one, any local webview could call them, even one granted no capability, such as stage 1.11's hidden evaluator. `default.json` grants them, with the HTTP plugin and its scope and the evaluator plugin (`fxm-evaluator:default`), to the main window's own webview (`"webviews": ["main"]`; a window's webview has the window's label), not to the main window: a capability that matches a window applies to every webview in it, so a child webview, such as an evaluator built inside the main window, would get all of it. Any other webview needs a capability of its own. The app registers no dialog plugin: only Rust opens dialogs.

**Dropping `unsafe-headers`.** `unsafe-headers` lets page script send forbidden headers to every host in the scope: the isolation hook drops `Cookie`, `Host` and `Proxy-*` and keeps `Origin` to a real site's, but others, such as `Referer`, still pass. [plugins-workspace PR #3703](https://github.com/tauri-apps/plugins-workspace/pull/3703) (open on 2026-10-26, last updated 2026-10-14) lets the app's config set or remove headers per URL instead (`requestHeaders`), and set the default User-Agent (`userAgent`). `request-headers.json` already holds FXM's rules in that shape: no `Origin` for any host, Spotify's own for Spotify; a test keeps them in step with `NATIVE_ORIGINS`. Once a plugin release with the PR is 14 days old:

1. Update `tauri-plugin-http` and `@tauri-apps/plugin-http` (in `packages/platform`).
2. Move the list into `tauri.conf.json` under `plugins > http > requestHeaders`, and delete `request-headers.json`.
3. Drop `unsafe-headers` from `Cargo.toml`, and update the tests that pin both.

The User-Agent needs no change: it isn't a forbidden header, so the web app keeps setting it per request.

### What page script can reach

Page script is anything that runs in the main webview: the web app, a module stage 1.13 loads, or a script injected by a bug. It reaches the network through every channel below, not only through `createDesktopFetch()`:

| Channel | What page script can do with it |
|---|---|
| `plugin:http\|fetch`, through Tauri's IPC | Send any method, body and header to the hosts in the scope. Whatever the message's shape or command, the isolation hook drops a proxy, TLS exceptions, `Cookie`, `Host` and `Proxy-*`, and keeps `Origin` to a real site's, except for a message that slips through its start-up gap (above): that one keeps all of them, the proxy included. `unsafe-headers` still lets page script set other forbidden headers, such as `Referer`, until it is dropped (above) |
| `user_host_fetch` | `GET` and `HEAD` to hosts the user approved, at public addresses only |
| `img-src https:` and `media-src https:` in the CSP | Load an image or a media file from any HTTPS host and port, the user's own network included, through the webview's own networking: a `GET` whose URL can carry data, and whose success or failure the page sees |
| `opener:default` | Open an `http(s):`, `mailto:` or `tel:` URL in the user's default browser or app, and show a file in the file manager |

So the approved list and the public-address filter bind `user_host_fetch` only, and the header rules bind `ctx.fetch` and, through the hook, the HTTP plugin, but for the hook's start-up gap. None of them keeps page script from contacting a host of its own choosing: the CSP's `img-src` and `media-src` let it. Narrowing those would break artwork and playback from hosts known only at run time, such as a user's Invidious instance.

**For stage 1.13.** The signed resolver module runs in this webview from a `blob:` URL, so everything in this table applies to it. "The platform host allowlists still apply, so a module can't reach new hosts" holds for what the module sends through `ctx.fetch` only. The isolation hook keeps the module from giving the plugin a proxy, TLS exceptions or a forbidden header, apart from its start-up gap. `blob:` joined `script-src` with stage 1.13 before that gap was closed, so closing it (see [The isolation hook](#network)) comes next. Keeping code that isn't FXM's out of this webview is the job of the module's signature check.

## Playback and OS integration

Stage 7.3 makes the desktop app a music player that keeps playing with its window closed. The web app's player (`@fxm/player`) plays with `<audio>`, as on the web; the desktop app adds its own rules, the tray, background playback and network notifications. The web app's side of all this is the bridge, `@fxm/desktop/bridge` (`bridge/`), and the web app builds its player with it when it runs in the desktop app:

```ts
import { createDesktopPlayback } from '@fxm/desktop/bridge'
import { isTauriRuntime } from '@fxm/platform'

const desktop = isTauriRuntime() ? createDesktopPlayback() : undefined
const lifecycle = new StreamLifecycle({ ...options, ...desktop?.lifecycleOptions })
const player = new Player({
  ...desktop?.playerOptions,
  engine: desktop?.createEngine() ?? new DirectAudioEngine(),
  resolver: lifecycle,
})
const disconnect = desktop?.connect(player) // the tray and the Web Lock
```

The web app keeps connecting the Media Session itself (`connectMediaSession`). Stage 2.5, which builds the web app's player, had not merged when 7.3 was built, so those lines wait for it; the live smoke test builds its player with exactly them.

| What | How | Code |
|---|---|---|
| `<audio src>` only for URLs that passed the probe | The engine says `no` to an IP-bound URL whose end-of-file probe didn't pass, and the player retries a song left with no such URL | `bridge/engine.ts`, `bridge/options.ts` |
| The codec per `canPlayType`, AAC on macOS before 15.4 | Opus 251 only where the engine says `probably`, which it never does on macOS before 15.4 | `bridge/engine.ts`, `src/environment.rs` |
| Re-resolving on a 403 or after about 5 hours | The stream lifecycle's status check, and a one-hour margin before URLs expire | `bridge/options.ts` |
| The URL cache follows the network | Native route changes, plus `online` and `offline` | `bridge/network.ts`, `src/network.rs` |
| A tray menu | Rust builds it; the player's state comes back through `set_now_playing` | `src/tray.rs`, `bridge/tray.ts` |
| Close to tray | The close button hides the window, to the tray where one shows (Windows, Linux) and to the Dock on macOS, leaving full screen first | `src/window.rs`, `src/fullscreen.rs` |
| Background throttling off | `backgroundThrottling: disabled` (macOS 14 and later), a Web Lock (Windows, Linux) | `tauri.conf.json`, `bridge/keep-awake.ts` |
| Media Session | The web app's, which each webview hands to the system's media controls | `@fxm/player` |

**`<audio src>` only for URLs that passed the probe.** The desktop app reads stream bytes through Rust, so the YouTube resolver (stage 1.4) fetches the last 64 KB of every file before it offers a URL: `fullLength` is `verified`, or `capped` for a URL that stops early, which never plays anywhere. `DesktopAudioEngine` (the direct audio engine with the desktop rules) also says `no` to an IP-bound URL that is still `unverified`, which happens when the probe got no answer. The player never hands the engine a stream it says `no` to, and the playback policy then takes the probed fallback rung (itag 18), then resolves again from the top. Free sources (Internet Archive, Jamendo) are not IP-bound, nothing caps them and nothing probes them, so they play as they are.

When no rung's probe answers, say on a flaky connection, the stream lifecycle finds nothing playable and rejects with `Unavailable` (`no-stream`), which the player's own classes skip at once. The desktop player retries it instead (`desktopClassifyFailure` in `bridge/options.ts`, part of `DESKTOP_PLAYER_OPTIONS`): after 0, 1 and 3 s, each time resolving the song afresh from the top rung, which probes again. A song still unplayable after those 3 retries is given up and counts toward the player's circuit breaker, which stops playback after 4 such songs in a row, as it does for network failures; the web app, which plays an unverified URL, would have played or retried it. The lifecycle takes such a retry for the user playing the song again, which matters only for a Suggest-band guess, and a resolution that held a guess back fails with `needs-review`, which is still skipped. Where the probe should get an answer more often is stage 1.4's to decide (its timeout and retries).

**The codec per `canPlayType`.** The playback policy plays Opus 251 only where the engine says `probably` for `audio/webm; codecs="opus"`, otherwise AAC 140 (`choosePlaybackStream`). WebKit plays Opus in WebM only from macOS 15.4, and a WKWebView's User-Agent says macOS 10.15.7 on every version, so the shell reports the real version (`desktop_environment`, from `NSProcessInfo`), and on earlier versions the engine rates Opus `maybe` at most, whatever WebKit answers: AAC plays whenever the song has it, and Opus remains the fallback. Until the shell has answered, a few milliseconds after start, only the probe rule applies. WebView2 answers `probably` for Opus, and so does WebKitGTK where GStreamer's base and good plugins are installed (AAC needs gst-libav).

**Re-resolving on a 403 or after about 5 hours.** An `<audio>` element never sees a status code, so after a playback failure the stream lifecycle asks the source for the URL's status with a ranged GET through Rust (`checkStatus`, stage 1.4): a 403 resolves the stream again, once on the same rung, then on the fallback, and a 403 on a cached URL also flushes the cache (a probable new IP address). YouTube's URLs expire about 6 hours after they were resolved, and the desktop app resolves them again once they are about 5 hours old (`DESKTOP_URL_REFRESH_MARGIN_MS`, one hour before `expire`, where the web app keeps 10 minutes): the URL cache stops handing them out, and the player refreshes a stream loaded that long ago, say before a long pause, before it plays again. The wider margin covers a long track that starts on an old URL, whose media element may ask for more bytes near its end, and a clock that is some minutes off.

**The network.** YouTube's URLs work only from the IP address that resolved them, so the stream lifecycle keys its cache by network. `src/network.rs` asks the operating system every 5 seconds which local address it would use to reach the internet, over IPv4 and IPv6, and tells the window (`fxm-network-change`) when either changes: a new Wi-Fi network, a cable, a VPN going up or down, a new temporary IPv6 address. Asking sends nothing: connecting a UDP socket only picks the route, and the destinations are documentation addresses (RFC 5737, RFC 3849). `createDesktopNetworkMonitor` turns that, plus the webview's `online` and `offline`, into the lifecycle's `NetworkMonitor`. It ignores the Network Information API, which only WebView2 has and whose estimates change on their own every few minutes.

**The tray.** Rust builds the tray icon (`src/tray.rs`), so it is there before the page loads and keeps working if the page hangs:

| Item | What it does |
|---|---|
| The current track and what the player does with it, or "Nothing playing" | Nothing, it informs; after an error, shows the window |
| Play / Pause | Plays or pauses: `fxm-media-action` with `toggle` |
| Next | The next track (`next`) |
| Previous | The previous track, or the start of this one after 3 s (`previous`) |
| Show FXM | Shows and focuses the window |
| Quit FXM | Quits |

The first line says what the player is doing, and the icon's tooltip says the same with the track (Windows and macOS; Linux status areas show no tooltips):

| The player | Menu | Tooltip |
|---|---|---|
| Nothing queued | Nothing playing | FXM |
| Playing, or loading the next track | Creep – Radiohead | FXM: Creep – Radiohead |
| Paused, stopped or not started | Paused · Creep – Radiohead | FXM: Paused · Creep – Radiohead |
| Stopped on an error the user must look at (a bot check, a login, too many failed tracks in a row) | Can't play: open FXM to see why | FXM: Can't play Creep – Radiohead |

The first line is disabled, so it only informs, except after an error: then choosing it shows the window, which says what went wrong. The media items are disabled while nothing is queued. A click on the icon shows the window on Windows; on macOS it opens the menu, as menu bar items do, and on Linux the status area always opens the menu. On macOS the icon is a template image of the FXM bars (`tray/36x36.png`), which macOS draws in the menu bar's own colour. Windows and Linux show an icon of their own (`tray/color/32x32.png`, from `assets/tray-color.svg`): the purple tile edge to edge with three bold bars, every edge on a 2 px grid, so it halves to a sharp 16 px, the notification area's size at 100% scaling. The app icon, drawn on the macOS icon grid with 3 px margins, shrank there to a 13 px tile whose five bars blurred into one.

`connectTray` (`bridge/tray.ts`) sends the player's state to `set_now_playing` whenever what the menu shows changes (`state`: `playing`, `paused` or `error`, with the title and artists), and runs the menu's media actions on the player. An update that fails is sent again, with the latest state, after 1 s, then 2, 4 and so on up to a minute while it keeps failing; updates wait for that retry, and the failure is reported once per run. Lone UTF-16 surrogates, such as a title cut in the middle of an emoji, become U+FFFD on the way (`wellFormed`): Rust's JSON parser refuses them, and every update for that track would fail. Rust caps what it shows (60 characters in the menu, 120 UTF-16 code units in the tooltip, which Windows cuts at 127) and doubles `&`, which menus read as a mnemonic marker; muda, Tauri's menu library, does the same for `_` in GTK menus. Whether the Windows tooltip drops a single `&` too is part of the [manual check](#manual-check).

Linux shows tray icons through an AppIndicator library (`libayatana-appindicator3` or `libappindicator3`), which tray-icon loads when the icon is built and panics without. FXM checks for it first, under the four names libappindicator-sys tries (the versioned `.so.1` files, then the unversioned `.so` that some AppImages bundle alone), and runs without a tray icon where none loads. The library alone shows nothing: a panel must host the icon, through the session bus's `org.kde.StatusNotifierWatcher`. KDE Plasma, Cinnamon, XFCE and most other panels do; GNOME does only with its AppIndicator extension. So at each close FXM also asks the watcher whether a host is registered (`IsStatusNotifierHostRegistered`, through gio), and quits rather than hides when none is or nothing answers within half a second. A panel that knows only the older XEmbed tray (i3bar, for one) may still show the icon through libappindicator's fallback, but FXM can't tell, so closing quits there too. The smoke build has no tray icon: it runs unattended and leaves the menu bar alone.

**The close button** (`close_action` in `src/window.rs`), whether or not music plays:

| | The close button, ⌘W, Alt+F4 |
|---|---|
| macOS | Hides the window; a window in full screen leaves full screen first |
| Windows, and Linux where a panel shows the tray icon | Hides the window to the tray; the first time, a notice says where FXM went and how to quit it |
| Linux without a tray icon (no AppIndicator library, or no panel that hosts it) | Quits |

On macOS FXM behaves like other Mac apps: closing the window leaves FXM in the Dock and the menu bar; clicking it in the Dock, Window > FXM (⌘0) or Show FXM in the menu bar brings the window back, and Quit (⌘Q) quits. Tauri's default app menu has no item for a hidden window, so `app_menu` adds Window > FXM, as Calendar has Window > Calendar; without it the keyboard could reach the window only through the Dock. A window in full screen first leaves it: hidden in full screen, it would leave its Space behind, empty and black, until the user swipes away (Electron apps meet the same, electron#20263). Tauri can't tell when the animation ends, since tao counts the window as windowed as soon as it is asked to leave, so `src/fullscreen.rs` waits for AppKit's `NSWindowDidExitFullScreenNotification` and hides the window then, unless the window was asked for again meanwhile or more than 5 s passed. It comes back, and FXM next opens, out of full screen.

On Windows and Linux FXM behaves like other tray apps: closing the window leaves FXM in the tray, playing or not, and Quit FXM in the tray menu quits. Windows puts a new app's icon in the overflow (the ^ next to the clock) until the user drags it onto the taskbar, so the music would play on with nothing in sight: the first time the window hides, a notice (a message box from rfd, as the approval dialog is, so the app still registers no dialog plugin) says where FXM went and how to quit it, and `tray-notice-shown` in the app's config folder remembers that it did. Where the desktop shows no tray icon, closing quits, so FXM never lingers out of sight. Launching FXM again always brings the window back.

**Background playback.** A hidden window's page must keep running: the player moves to the next track, retries and watches for stalls on timers and events.

- **macOS:** `backgroundThrottling: disabled` on the window, which Tauri turns into WebKit's `inactiveSchedulingPolicy` none (macOS 14 and later). Without it, the smoke test's hidden page stopped while its muted track played (see [Live smoke test](#live-smoke-test)).
- **Windows and Linux:** Tauri has no such switch for WebView2 or WebKitGTK, and its documentation suggests a pending Web Lock. `keepAwakeWhilePlaying` (`bridge/keep-awake.ts`) holds a shared Web Lock, `fxm-background-playback`, while the player is playing or loading the next track, and releases it on pause, so an idle FXM in the tray is throttled as usual. Chromium, and so WebView2, never freezes a page that holds a Web Lock; whether the lock also spares it the intensive throttling of timers that starts after 5 minutes hidden is what the smoke test's 9-minute playlist shows on WebView2, and the player moves between tracks on media events, which that throttling leaves alone. Whether WebKitGTK gains anything from the lock is part of the [manual check](#windows-and-linux). The lock is held on macOS too, where it costs nothing. macOS 11 to 13 have no inactive scheduling policy: there, playback relies on WebKit keeping a page that plays audio running, and whether the lock adds anything is untested.

The webviews allow audio to start without a user gesture (wry's default), so tracks follow one another while the window is hidden.

**Media Session and media keys.** The web app connects its player to the Media Session (`connectMediaSession`, stage 2.2), and each webview hands that to the system:

| | Media controls | Notes |
|---|---|---|
| macOS (WKWebView) | Now Playing in Control Center, media keys | Measured in a WKWebView harness by the research, and the smoke test checks the Media Session's titles |
| Windows (WebView2) | The media flyout, the lock screen, media keys | The flyout names the app "Unknown app": the Media Session belongs to WebView2's browser process (`msedgewebview2.exe`), not to FXM, an open WebView2 bug ([WebView2Feedback#2236](https://github.com/MicrosoftEdge/WebView2Feedback/issues/2236)). The controls, the title and the artwork work; only the app's name is wrong. Fixing it would take FXM's own System Media Transport Controls from Rust, with WebView2's own media keys turned off: not done |
| Linux (WebKitGTK) | MPRIS (desktop media widgets, `playerctl`), where WebKitGTK is built with the Media Session | Part of the manual check; the tray works either way |

**Capabilities.** The web app's capability grants Tauri's `core:default` minus `core:tray:default` and `core:menu:default`, so page script can neither change the tray nor add tray icons or menus of its own. `set_now_playing` and `desktop_environment` join the app's commands, each behind a permission, for the main window's own webview only. The page's text in the tray is untrusted input to Rust: it arrives through a struct that refuses unknown fields and states, and Rust drops control characters and caps its length.

## Content security policy

```
default-src 'self'; img-src 'self' https: data: blob:; media-src 'self' https: blob:;
connect-src ipc: http://ipc.localhost 'self'; script-src 'self' 'wasm-unsafe-eval' blob:;
style-src 'self' 'unsafe-inline'
```

- `connect-src` has no `https:`: `fetch()`, `XMLHttpRequest`, `WebSocket` and `EventSource` reach only Tauri's IPC (`ipc:` on macOS and Linux, `http://ipc.localhost` on Windows), so every request FXM makes goes through Rust, with its scope and header policy. A stray `fetch()` from page script is blocked instead of going out with the webview's origin and cookies. It doesn't keep page script off the network: see [What page script can reach](#what-page-script-can-reach).
- `media-src https:` lets `<audio>` play googlevideo URLs directly, as well as Internet Archive's and Jamendo's media hosts and a user's Invidious instance, whose hosts can't be listed at build time. The page can't read those responses. `img-src https:` does the same for artwork.
- At build time Tauri adds the isolation hook's own origin to `default-src`, for its iframe.
- At build time Tauri adds the SHA-256 hash of every inline script to `script-src`, so the theme script in `apps/web/index.html` keeps running.
- `blob:` in `script-src` lets the app run the signed YouTube resolver module it downloads from FXM's site (stage 1.13): the module's bytes are checked against their Ed25519 signature first, then loaded from a `blob:` URL made from exactly those bytes, which is revoked once loaded. It also lets the page run its other `blob:` URLs (artwork, audio) as scripts, which would matter only together with an injected `<script>` element naming one. The web app's own policy has no `blob:` there: it gets new code by redeploy. See [packages/platform/src/updates](../../packages/platform/src/updates/README.md).
- **No `'unsafe-eval'`.** The app's policy has none. Stage 1.11 kept it out: YouTube's player script and BotGuard run in the hidden evaluator webview, whose scheme handler sets its own policy, so no fallback to `'unsafe-eval'` here was needed. Stage 7.2 added none either.

## Releases

Every release builds the desktop app: `release.yml` calls `.github/workflows/desktop-release.yml` with the commit and version it releases, then publishes what that uploads with the rest of the release ([docs/WORKFLOW.md, "Releases"](../../docs/WORKFLOW.md#8-releases)). tauri-action builds each target on a runner of its own, with `src-tauri/tauri.release.conf.json` merged over the config, which turns on the updater's files:

| Target | Runner | Files in the release |
|---|---|---|
| macOS, Apple silicon | `macos-latest` | `fxm-desktop-<version>-macos-arm64.dmg`, and its `.app.tar.gz` for the updater |
| macOS, Intel | `macos-latest`, cross-compiled | `fxm-desktop-<version>-macos-x64.dmg`, and its `.app.tar.gz` |
| Windows x64 | `windows-latest` | `fxm-desktop-<version>-windows-x64-setup.exe` (NSIS, for one account) and `-windows-x64.msi` (for every user) |
| Linux x64 | `ubuntu-22.04` | `fxm-desktop-<version>-linux-x64.deb` and `-linux-x64.AppImage` |
| Linux arm64 | `ubuntu-22.04-arm` | `fxm-desktop-<version>-linux-arm64.deb` and `-linux-arm64.AppImage` |

And `latest.json`, the updater's manifest. `release/targets.ts` lists the targets and their files, and R.1's catalog (`fxm_release_catalog` in `scripts/release-lib.sh`) the same files, which a test keeps equal. Every name follows the release's own, `fxm-desktop-<version>-<os>-<cpu>`, with x64 and arm64 whatever a format calls them; `latest.json` alone has a fixed name, which installed apps look up. Linux builds on Ubuntu 22.04, so its files need glibc 2.35 or later. No `.rpm`: other distributions get the AppImage, and Flathub with stage R.3. How users install each file is in [INSTALL.md](INSTALL.md).

**Signing.**

- **macOS:** signed ad hoc (`bundle > macOS > signingIdentity` `"-"`), with the hardened runtime that Tauri turns on, and not notarized: FXM joins no Apple program ([docs/ARCHITECTURE.md §1](../../docs/ARCHITECTURE.md#non-goals)). Apple silicon calls an unsigned app from the internet "damaged"; signed ad hoc, it gets Gatekeeper's warning and "Open Anyway". The build checks the signature (`codesign --verify --deep --strict`, `Signature=adhoc`). `make desktop-build` signs ad hoc too, so local builds match: on 2026-10-26, on macOS 15.5 (Apple M4), `codesign --verify --deep --strict` passed with `flags=0x10002(adhoc,runtime)` and sealed resources, and `spctl --assess` rejected the app, as Gatekeeper does until the user chooses "Open Anyway". No Homebrew cask while the app isn't notarized: Homebrew disables casks that fail Gatekeeper.
- **Windows:** unsigned, so SmartScreen warns about the installers and Smart App Control blocks them. Free signing through SignPath Foundation or OSSign is stage 7.6's, once one of them accepts FXM.
- **Linux:** nothing to sign. Each release's `SHA256SUMS` and attestations cover every platform's files.

**GStreamer.** WebKitGTK plays audio with GStreamer: Opus, Vorbis, MP3 and FLAC need its base and good plugins, and AAC (YouTube's AAC 140, and the itag 18 fallback) needs gst-libav.

- The `.deb` depends on `gstreamer1.0-plugins-base`, `gstreamer1.0-plugins-good`, `gstreamer1.0-libav` and an audio output (`gstreamer1.0-pulseaudio | gstreamer1.0-alsa`), besides what Tauri adds itself (`libwebkit2gtk-4.1-0`, `libgtk-3-0`, `libayatana-appindicator3-1`), in the `sound` section. Debian's and Ubuntu's WebKitGTK depend on base and good already, but Ubuntu's only suggests gst-libav, which is in universe there.
- The AppImage bundles GStreamer (`bundleMediaFramework`), so it plays with its own copy and none of the host's plugins. The release installs base, good and the audio outputs only, all LGPL, and `release/gstreamer-check.sh` stops a build that would bundle gst-libav, ugly or bad: gst-libav decodes with Ubuntu's FFmpeg, which has GPL parts. So the AppImage plays Opus, Vorbis, MP3 and FLAC, but no AAC: a song that only resolves to AAC plays with the `.deb`, not with the AppImage. An LGPL-only FFmpeg build in the AppImage would fix that: not done.

**The AppImage's tools.** The bundler makes the AppImage with tools that it downloads from GitHub releases the first time and runs unchecked: the AppImage's entry point (`AppRun`), linuxdeploy and linuxdeploy's AppImage plugin, whose `continuous` release is rebuilt every month. The plugin's appimagetool downloads the AppImage runtime as well, the first bytes of the file, from type2-runtime's `continuous` release. The release signs the AppImage with the updater key, so whatever those tools put into it would reach every installed AppImage as an update. So each Linux build first fetches them, and the runtime, from releases that aren't rebuilt (`release.ts appimage-tools`), checks each against the SHA-256 in `release/appimage-tools.ts`, and puts them in the bundler's tools folder (`target/.tauri`, with `useLocalToolsDir`), which it looks in before it downloads anything; appimagetool gets the runtime as `LDAI_RUNTIME_FILE`. A file that doesn't match stops the build before anything runs it. After the build, a check stops the job if the folder holds a tool that the bundler fetched itself, or if an AppImage doesn't start with the pinned runtime, byte for byte but for the 16-byte digest that appimagetool writes into it. `desktop.yml`'s builds, whose files are never released, still let the bundler fetch them.

**The updater's files.** `tauri build` makes them only with a signing key (`TAURI_SIGNING_PRIVATE_KEY`), which it signs them with. The build jobs run the code of hundreds of crates and npm packages, so they never get the updater key: each one makes a throwaway key (`release.ts build-key`), and Tauri warns that it doesn't match the apps' public key. The sign job then gathers every build's files, signs the ones the updater installs with the updater key (`release.ts sign`, with Node's own crypto in `release/minisign.ts`: the job installs nothing), writes `latest.json` and checks every signature against the public key the apps carry, as each platform's updater will.

**Dry run.** Start `desktop.yml` by hand with `release-dry-run` (`scripts/run.sh gh workflow run desktop.yml --ref <branch> -f release-dry-run=true`, or Actions → Desktop → Run workflow). It runs `desktop-release.yml` on the branch's commit with the version in `apps/desktop/package.json`: every target builds, its apps carrying its build's throwaway public key in place of the placeholder (which can't build updater files), and the sign job signs with a throwaway key of its own, so no installed app would accept a dry run's update. The files stay with the run, as artifacts: `release-desktop`, the release's files and `latest.json`, for 30 days, and each target's own for 7. Nothing is published or tagged, and no secret is read. Locally, `make desktop-build` builds this machine's target without the updater's files, so it needs no key.

The first dry run, on 2026-10-26 ([run 40264753607](https://github.com/Pratyay-ops/FXM/actions/runs/40264753607), version 0.0.0), passed on every target. Its `release-desktop` held the ten installers and updater files (from 4.1 MB for the Windows installer to 95 MB for the x64 AppImage) and `latest.json`, with the 13 platforms each signed for version 0.0.0, and `scripts/release-collect.sh` took all eleven. Both `.app.tar.gz` held `FXM.app` alone, without AppleDouble files, its ad-hoc signature valid once extracted (arm64 and x86_64). The arm64 `.deb` asked for `gstreamer1.0-plugins-base, gstreamer1.0-plugins-good, gstreamer1.0-libav, gstreamer1.0-pulseaudio | gstreamer1.0-alsa, libayatana-appindicator3-1, libwebkit2gtk-4.1-0, libgtk-3-0`, and both AppImages bundled the GStreamer plugins of base (28), good (72), alsa, gl, x and GStreamer's core only. `gstreamer1.0-pulseaudio` brought no plugin of its own: since Debian 11 and Ubuntu 22.04 it is a transitional package, and the PulseAudio plugin is part of good. Where a distribution drops it, the `.deb`'s dependency falls back to `gstreamer1.0-alsa`.

The second, also on 2026-10-26 ([run 40274843619](https://github.com/Pratyay-ops/FXM/actions/runs/40274843619)), built the AppImages with the pinned tools and passed on every target. Each Linux job fetched the four files with their pinned SHA-256, the bundler downloaded none of them (the first run's log shows its three downloads), and the tools folder held nothing else after the build. The x86_64 AppImage's first 944,632 bytes were those of type2-runtime 20251108, but for one run of 16 bytes, the digest; the runtime check, added after this run, accepts that AppImage.

## Updates

The app looks for a newer version and installs it once the user agrees (`src/updater.rs`), through tauri-plugin-updater. Only Rust uses the plugin: the web app's capability grants none of its commands, so no page script, a signed resolver module included, can check, download or install anything.

- **When.** In release builds that carry a real key only: 10 seconds after FXM starts, then every 24 hours while it runs (it can stay in the tray for days), or an hour after a check that failed. Debug builds (`make desktop-dev`, the smoke test) and builds with the placeholder never look.
- **Where.** `https://github.com/Pratyay-ops/FXM/releases/latest/download/latest.json` (`plugins > updater > endpoints`): the latest release's manifest, which GitHub redirects to its download host. The request carries the plugin's User-Agent, `tauri-plugin-updater/<version>`. The site's privacy page says that the apps check GitHub for updates.
- **Asking.** A native dialog, as when FXM asks before contacting a new host (rfd), and only while FXM's window is in front: never over another app, never from the tray, where the offer waits for the window. "Later" is the button Return presses on macOS and Windows, and the next check offers the version again. "Install and Restart" downloads it, with the progress in the window's title, checks it, installs it and starts FXM again. A failure is told in a message, with the release page's address.
- **Stalls.** The check and the download give up when nothing arrives for a minute (and connecting gives up after 30 s; the whole check, `latest.json`, after a minute), as when a laptop sleeps or the Wi-Fi changes mid-download: without a limit, reqwest would wait for ever, the title would stay at its last percentage and FXM would look for updates again only after a restart. A download that gave up is told like any other failure.
- **Installing.** macOS replaces `FXM.app` where it is (with an administrator's password when its folder needs one); Windows runs the new NSIS installer or MSI in passive mode (`plugins > updater > windows > installMode`), which closes FXM and opens it again; Linux replaces the AppImage. The plugin picks the file by the bundle the running app came from: the bundler marks each bundle's executable, and `latest.json` lists `<os>-<arch>-<bundle>` for each (`darwin-aarch64-app`, `windows-x86_64-msi`, `linux-x86_64-deb`, …), and `<os>-<arch>` for an app without a mark (the `.app.tar.gz`, the NSIS installer, the AppImage). So an MSI installation never gets the NSIS installer, nor a `.deb` installation the AppImage.
- **The `.deb`.** apt installed it, so apt updates it: for a `.deb` installation the offer names the new version and the file to install with `sudo apt install`, and its button, "Open Release Page", opens the release in the browser. FXM installs nothing itself there, because the plugin would run `dpkg -i` through pkexec and, when that fails or the user cancels the system's password prompt, ask for the password again in a dialog of its own (zenity or kdialog), pipe it to `sudo -S`, and fall back to `sudo` in a terminal last: cancelling wouldn't cancel the install, and the user's password would pass through FXM. `latest.json` still lists the `.deb`s, so such an installation finds its new version.
- **Trust.** The plugin installs a download only when its signature holds under the public key in `tauri.conf.json` (minisign, Ed25519). `requireSignedVersion` also has it check the version that the signature's trusted comment names against the version that `latest.json` announces: `latest.json` itself isn't signed, and without the check, whoever could serve one could pair a new version number with an older, validly signed release. No `dangerous…` setting, and no `allowDowngrades`.

### The updater key

A minisign key pair (Ed25519), made with the Tauri CLI. Every app carries the public key, which is committed in `tauri.conf.json`; the secret key signs every release, and only the release workflow's sign job gets it, from the `desktop-updater` environment, once the owner has approved the run. **Until the owner commits FXM's public key, `tauri.conf.json` holds a placeholder: every release stops at its first job (`release.ts check`), and no build looks for updates.**

1. Make the pair outside the repository, with a password, which the CLI asks for twice. It never overwrites an existing key without `--force`. Give it an absolute path: `pnpm exec` runs in `apps/desktop`.

   ```sh
   mkdir -p ~/FXM-keys && chmod 700 ~/FXM-keys
   scripts/run.sh pnpm --filter @fxm/desktop exec tauri signer generate -w ~/FXM-keys/fxm-desktop-updater.key
   ```

   It writes the secret key to `fxm-desktop-updater.key`, readable by you only, and the public key to `fxm-desktop-updater.key.pub`, each as one line of base64.
2. Put the public key, the content of `fxm-desktop-updater.key.pub`, in `plugins > updater > pubkey` in `src-tauri/tauri.conf.json` in place of the placeholder, and commit it (`chore(desktop): trust the updater key`).
3. Set up the `desktop-updater` environment once, before adding the key: only runs on `main` may use it, and you approve each one, so every release waits for you before its sign job gets the key. Neither a pushed branch with a changed workflow nor a pull request merged into `main` by mistake, or by a tool, can then sign anything. On GitHub, open **Settings → Environments → New environment**, name it `desktop-updater` and click **Configure environment**; under **Deployment branches and tags**, choose **Selected branches and tags** and add a rule for the branch `main`; under **Required reviewers**, add yourself, and leave **Prevent self-review** off so that you can approve your own releases. Or, from the repository folder:

   ```sh
   owner_id=$(scripts/run.sh gh api users/Pratyay-ops --jq .id)
   scripts/run.sh gh api -X PUT repos/Pratyay-ops/FXM/environments/desktop-updater --input - <<EOF
   {
     "reviewers": [{ "type": "User", "id": $owner_id }],
     "prevent_self_review": false,
     "deployment_branch_policy": { "protected_branches": false, "custom_branch_policies": true }
   }
   EOF
   scripts/run.sh gh api -X POST repos/Pratyay-ops/FXM/environments/desktop-updater/deployment-branch-policies \
     -f name=main -f type=branch
   ```

   The sign job names the environment, so a release run would create it empty, with neither rule, if it didn't exist yet. Keep `main` protected and admin rights to yourself, as [Protect the store keys](../extension/README.md#protect-the-store-keys) says for the `stores` environment: whoever can push to `main` directly, or change the environment, can get around both rules.
4. Add the secret key and its password as secrets of that environment, never as repository secrets, which a workflow run from any pushed branch can read:

   ```sh
   scripts/run.sh gh secret set TAURI_SIGNING_PRIVATE_KEY --env desktop-updater < ~/FXM-keys/fxm-desktop-updater.key
   scripts/run.sh gh secret set TAURI_SIGNING_PRIVATE_KEY_PASSWORD --env desktop-updater
   ```

   `release.yml` passes both names on to `desktop-release.yml`, as GitHub needs for an environment's secret to reach a called workflow's job, and the sign job, which names the environment, gets the environment's values. When a release run reaches it, GitHub asks you to approve (**Review deployments** on the run's page): the sign job, and so the release, waits until you do.
5. Keep the secret key and its password offline too, in a password manager. Without them, no installed app can be updated any more, and their users would have to install the next version by hand. Whoever has both can sign updates that every installed FXM accepts, wherever they manage to publish them.

`release.ts sign` refuses a key whose public key isn't the one in `tauri.conf.json`, since the apps would refuse every update it signs. Changing keys therefore takes one release signed with the old key whose apps carry the new public key, which needs a one-off change to that check; it hasn't been needed.

Still to check, once two releases are out: an update from one to the next on each OS, to record in the [manual check's results](#results-of-the-manual-check). On macOS that includes whether App Management (System Settings → Privacy & Security, macOS 13 and later) asks before an app signed ad hoc replaces its own bundle, and on Windows whether the passive installer runs without a SmartScreen prompt.

## Maintenance

**Icons.** Edit `assets/icon.svg`, then run `scripts/run.sh pnpm --filter @fxm/desktop icons` from the repo root. The tray icons have sources of their own: `assets/tray-template.svg` for the macOS menu bar, the bars alone in black on a 36 px canvas (18 pt at 2x), and `assets/tray-color.svg` for Windows and Linux, the tile edge to edge on a 32 px canvas, every edge on a 2 px grid so it halves cleanly to 16 px. Run `scripts/run.sh pnpm --filter @fxm/desktop tray-icon` after editing either. The mark sits on the macOS icon grid (an 824 px body on a 1024 px canvas), so it lines up with other apps in the Dock. `tauri icon` writes the entries of `icon.icns` in a different order on every run, so that file shows up as changed even when the art didn't.

**Versions.** Every pin follows the repo's 14-day rule (see [DEVELOPMENT.md](../../docs/DEVELOPMENT.md)):

| What | Pinned in | Notes |
|---|---|---|
| Rust | `src-tauri/rust-toolchain.toml` | 1.98.1. 1.99.0 miscompiles FFI `bool` returns on x86_64 ([rust-lang/rust#163911](https://github.com/rust-lang/rust/issues/163911)), and the fixed 1.99.1 is too new |
| rustup | `scripts/install-rust.sh` | Version plus one SHA-256 per platform, from `https://static.rust-lang.org/rustup/archive/<version>/<target>/rustup-init.sha256` |
| Crates | `src-tauri/Cargo.lock` | See below |
| `@tauri-apps/cli`, `@tauri-apps/api` | `package.json` | pnpm's `minimumReleaseAge` applies. Keep `@tauri-apps/api` on the same minor version as the `tauri` crate: `tauri build` refuses mismatched versions |
| `@tauri-apps/plugin-http` | `packages/platform/package.json` | The same minor version as the `tauri-plugin-http` crate (2.8), for the same reason |
| `tauri-plugin-updater` | `src-tauri/Cargo.toml` | Without its `zip` feature, which only reads Tauri 1's zipped and tarred bundles. No JavaScript package: only Rust uses it |
| tauri-action | `.github/workflows/desktop-release.yml` | v1.0.0, pinned to its commit like every action |
| AppImage tools | `release/appimage-tools.ts` | The files the CLI's bundler looks for when it builds an AppImage (`AppRun`, linuxdeploy `07333c6` and its AppImage plugin `1-alpha-20250213-1`) and the AppImage runtime (type2-runtime `20251108`), each with its SHA-256, for `@tauri-apps/cli` 2.12.2 (`TAURI_CLI`). A test and the release workflow refuse any other version of the CLI until they are refreshed; see below |

Cargo has no stable equivalent of pnpm's `minimumReleaseAge`, so re-resolve the whole lockfile with a publish-date cutoff 14 days back:

```sh
cd apps/desktop/src-tauri
cutoff=$(node -p 'new Date(Date.now() - 14 * 864e5).toISOString().slice(0, 19) + "Z"')
RUSTC_BOOTSTRAP=1 ../../../scripts/run.sh cargo generate-lockfile -Zunstable-options --publish-time "$cutoff"
```

`RUSTC_BOOTSTRAP=1` unlocks Cargo's unstable `--publish-time` flag for this one command, which only resolves versions and compiles nothing. Builds always use `--locked` in CI.

**Signatures.** `release/minisign.ts` reads and writes the formats of the minisign crate 0.9, which the Tauri CLI 2.12 signs with, and minisign-verify 0.3, which tauri-plugin-updater 2.13 checks with, and writes the trusted comment as the CLI does (`timestamp:…`, `file:…`, `version:…`). Its tests make key pairs and signatures with the Tauri CLI from `node_modules`, and a Rust test checks one of its signatures with minisign-verify (`test/fixtures/updater`), so a change to either side's format fails them. After updating the Tauri CLI or the plugin, compare `src/helpers/updater_signature.rs` (tauri-cli) and `verify_signature` (tauri-plugin-updater) between the releases.

**AppImage tools.** After updating `@tauri-apps/cli`, refresh `release/appimage-tools.ts` before the next release. Look up the tauri-bundler release that the CLI's crate depends on (on crates.io: `=2.10.2` for the CLI 2.12.2) and compare `prepare_tools` in its `src/bundle/linux/appimage/linuxdeploy.rs` with the list: the file names (linuxdeploy's carries `LINUXDEPLOY_COMMIT_HASH`), the releases they come from, and any file added. Take each file from a dated release, never `continuous`, with its SHA-256 from GitHub (`scripts/run.sh gh api repos/<owner>/<repo>/releases/tags/<tag> --jq '.assets[] | [.name, .digest]'`) or from the downloaded file (`shasum -a 256`). Check that linuxdeploy-plugin-appimage still passes `LDAI_RUNTIME_FILE` on to appimagetool as `--runtime-file` (its `src/main.cpp`). Then set `TAURI_CLI` to the new version, and start a release dry run to see the AppImages build.

**Tauri updates.** The isolation hook depends on how Tauri's frame serializes and sends a payload, and on the plugin's request fields. `test/isolation.test.ts` copies both from tauri 2.12.3, tauri-utils 2.10.1 and tauri-plugin-http 2.8.2, and fails once `Cargo.lock` holds other releases of them. Compare `scripts/process-ipc-message-fn.js` and `scripts/ipc.js` (tauri), `src/pattern/isolation.js` (tauri-utils), `src/ipc/protocol.rs` (tauri, how Rust reads a payload) and `ClientConfig` in `src/commands.rs` (tauri-plugin-http) between the releases. Adjust the hook and the test's copy to any change, then update the versions in the test.
