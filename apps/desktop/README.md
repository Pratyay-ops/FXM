# @fxm/desktop

The FXM desktop app for macOS, Windows and Linux: the web app (`apps/web`) in a [Tauri 2](https://v2.tauri.app) shell. This is FXM's installable "applet". It reaches YouTube, Spotify and every other service through native networking in Rust (tauri-plugin-http), so it needs no FXM Connect extension. Stage 7.1 built the shell, stage 7.2 its networking and stage 7.3 its playback and OS integration: a tray menu, a close button that keeps the music playing, playback in a hidden window and the system media controls.

Setup, prerequisites per OS, commands and disk usage are in [DEVELOPMENT.md → Desktop app](../../docs/DEVELOPMENT.md#desktop-app). In short:

```sh
make desktop-setup   # pinned Rust into .tools/, plus dependencies
make desktop-dev     # web dev server on port 5260 + the app window, with hot reload
make desktop-build   # FXM.app on macOS (all bundle types elsewhere), in src-tauri/target/release/bundle/
make desktop-check   # rustfmt, clippy, cargo test
scripts/run.sh pnpm --filter @fxm/desktop smoke   # the live smoke test, in a hidden window
```

## How it works

- **Frontend.** `tauri build` runs `pnpm --filter @fxm/web build:desktop`, which builds the web app with base `/` into `apps/web/dist-desktop`. Tauri embeds that folder in the executable and serves it from `tauri://localhost` (`http://tauri.localhost` on Windows). The router takes its basename from `import.meta.env.BASE_URL`, so nothing in the web app changes. Unknown paths fall back to `index.html`, so reloading a deep link works.
- **Development.** `make desktop-dev` starts Vite with `--base=/ --port 5260 --strictPort` and points the window at `http://localhost:5260`. Release-only behaviour, the CSP in particular, needs `make desktop-build`.
- **Window.** One window labelled `main`: 1200×800, at least 360×600, titled FXM, with the dark theme's background (`#0b0b0f`) until the page paints. tauri-plugin-window-state restores its size, position, maximized and full-screen state, but never starts it hidden. tauri-plugin-single-instance brings it to the front when FXM is launched a second time, also when it was hidden in the tray. Its close button may hide it instead of quitting, and its page keeps running while hidden: see [Playback and OS integration](#playback-and-os-integration). `dragDropEnabled: false` leaves drag and drop to the page, as in a browser: Tauri's native file-drop handling would turn off HTML5 drag and drop on Windows, which playlist reordering may rely on.
- **Links.** tauri-plugin-opener opens `target="_blank"` links in the default browser.
- **Network.** Every request goes through Rust: see [Network](#network) below.
- **Playback.** `<audio>` in the webview, as on the web, with the desktop app's rules, a tray menu and background playback: see [Playback and OS integration](#playback-and-os-integration).
- **No updater yet.** Stage 7.5 adds the updater, installers on GitHub Releases and macOS signing.

The tests in `test/` pin the CSP, the http plugin's scope and settings, the permissions around them, `default.json` as the only capability file, the app's commands, the plugins `src/lib.rs` registers, the tray feature and the window's background throttling, so widening any of them is always a deliberate change.

## Network

The web app never uses the webview's own `fetch` here. In the desktop app, `createPlatform()` from `@fxm/platform` sees Tauri's runtime and sends every provider request through `createDesktopFetch()` ([`packages/platform/src/desktop.ts`](../../packages/platform/src/desktop.ts)), which hands it to tauri-plugin-http in Rust. From the webview, a request would carry the app's own origin, which InnerTube refuses with 403 (`tauri://localhost` on macOS and Linux, `http(s)://tauri.localhost` on Windows, the dev server's under `make desktop-dev`), and the webview's cookies.

**Headers.** The policy is the native transport's (`NATIVE_ORIGINS` in [`packages/platform/src/native.ts`](../../packages/platform/src/native.ts)), and `createDesktopFetch()` enforces it once more at the last step:

| Requests to | `Origin` | `User-Agent`, unless the request names one |
|---|---|---|
| YouTube: InnerTube, `sw.js_data`, the player JavaScript, googlevideo | None | The webview's own, which is a browser's: WebView2's, WebKitGTK's, or on macOS WKWebView's completed to Safari's |
| Spotify | `https://open.spotify.com` | The same browser agent |
| Every other host | None | FXM's: `FXM ( https://github.com/Pratyay-ops/FXM )`, as MusicBrainz asks apps to name themselves |

- Headers travel only in `init.headers`, as a plain object: the plugin reads forbidden headers such as `Origin` only from there, and a `Request` object's headers would lose them.
- "None" is `origin: ''`, which the plugin removes. That takes the `unsafe-headers` feature: without it the plugin always adds the webview's origin. A missing or non-`https:` origin is turned into none, so no request can ever carry the webview's.
- The plugin's own agent, `tauri-plugin-http/<version>`, never goes out: Spotify refuses it, and it would single out FXM's traffic.
- InnerTube calls keep the CORS-simple shape of every platform and draw from the request budget, with `visitorData` in the request body. The session's visitorData is server-issued: native requests can read `https://www.youtube.com/sw.js_data`, which the YouTube provider (stage 1.3) takes it from.

**Scope.** `capabilities/default.json` lets the plugin reach exactly the hosts in the platform's host table (`HOST_RULES` in [`packages/platform/src/hosts.ts`](../../packages/platform/src/hosts.ts)), HTTPS only, and Last.fm only under `/player/station/`. The test builds the expected list from the table, so a host added there fails it until it is added here too. `scopeRedirects` in `tauri.conf.json` checks every redirect against the same scope, so a redirect elsewhere fails (`Unsupported`); googlevideo's redirects to other `*.googlevideo.com` hosts and Internet Archive's to its storage hosts, such as `dn710102.ca.archive.org`, stay inside.

**No cookie jar.** The plugin's default `cookies` feature is off. It would save every response cookie in plain text in `.cookies` in the app's cache folder and send it back with later requests. FXM never sends a `Cookie` header from the web app, and `Set-Cookie` never reaches page JavaScript. Stage 7.4 decides how Spotify credentials are stored.

**Hosts the user adds.** Tauri can't change a plugin's scope at runtime, so hosts typed into Settings, such as an Invidious instance or a Spotify secret source, go through the app's own commands in `src/user_hosts.rs`:

| Command | What it does |
|---|---|
| `user_hosts` | Lists the approved hosts |
| `approve_user_host` | Asks the user, in a native dialog over the main window, whether FXM may contact the host. Only a public domain name, with an optional port, can be approved: no IP address, no single-label name, no `.local`, `.lan`, `.internal` and the like |
| `revoke_user_host` | Removes a host |
| `user_host_fetch` | Fetches from an approved host |

- Only the user can grow the list, by saying yes in the dialog: page script, a resolver module included, can read and shrink it but never add to it, so it can't make FXM contact a host of its own choosing.
- `user_host_fetch` sends `GET` and `HEAD` only, over HTTPS, without cookies, credentials, a proxy or any header from the page, with FXM's User-Agent. Names must resolve to public internet addresses: loopback, private, link-local, shared and other special-purpose addresses are dropped after DNS resolution, so an approved name can't point FXM into the user's network. At most 5 redirects, each to an approved host; at most 8 MiB in 30 s. `Set-Cookie` is dropped.
- The list lives in `user-hosts.json` in the app's config folder (on macOS, `~/Library/Application Support/io.github.pratyayops.fxm/`).
- In the web app, `createDesktopUserHosts()` from `@fxm/platform` wraps the commands. Pass `userHosts: () => hosts.current()` to `createPlatform()`, so the transport routes those hosts; Rust checks them again on every request.

**App commands and permissions.** `build.rs` lists the app's commands in an app manifest, which gives each an `allow-…` permission and makes Tauri check app commands against the capabilities, as it does plugin commands. Without one, any local webview could call them, even one granted no capability, such as stage 1.11's hidden evaluator. `default.json` grants them to the main window only, and grants no `dialog:` permission: only Rust opens dialogs.

**Dropping `unsafe-headers`.** `unsafe-headers` lets page script send any forbidden header, `Cookie` and `Host` included, to every host in the scope. [plugins-workspace PR #3703](https://github.com/tauri-apps/plugins-workspace/pull/3703) (open on 2026-10-26, last updated 2026-10-14) lets the app's config set or remove headers per URL instead (`requestHeaders`), and set the default User-Agent (`userAgent`). `request-headers.json` already holds FXM's rules in that shape: no `Origin` for any host, Spotify's own for Spotify; a test keeps them in step with `NATIVE_ORIGINS`. Once a plugin release with the PR is 14 days old:

1. Update `tauri-plugin-http` and `@tauri-apps/plugin-http` (in `packages/platform`).
2. Move the list into `tauri.conf.json` under `plugins > http > requestHeaders`, and delete `request-headers.json`.
3. Drop `unsafe-headers` from `Cargo.toml`, and update the tests that pin both.

The User-Agent needs no change: it isn't a forbidden header, so the web app keeps setting it per request.

## Playback and OS integration

Stage 7.3 makes the desktop app a music player that keeps playing with its window closed. The web app's player (`@fxm/player`) plays with `<audio>`, as on the web; the desktop app adds its own rules, the tray, background playback and network notifications. The web app's side of all this is the bridge, `@fxm/desktop/bridge` (`bridge/`), and the web app builds its player with it when it runs in the desktop app:

```ts
import { createDesktopPlayback } from '@fxm/desktop/bridge'
import { isTauriRuntime } from '@fxm/platform'

const desktop = isTauriRuntime() ? createDesktopPlayback() : undefined
const lifecycle = new StreamLifecycle({ ...options, ...desktop?.lifecycleOptions })
const player = new Player({
  ...desktop?.playerOptions,
  engine: desktop?.createEngine() ?? new DirectAudioEngine(),
  resolver: lifecycle,
})
const disconnect = desktop?.connect(player) // the tray and the Web Lock
```

The web app keeps connecting the Media Session itself (`connectMediaSession`). Stage 2.5, which builds the web app's player, had not merged when 7.3 was built, so those lines wait for it; the live smoke test builds its player with exactly them.

| What | How | Code |
|---|---|---|
| `<audio src>` only for URLs that passed the probe | The engine says `no` to an IP-bound URL whose end-of-file probe didn't pass, and the player retries a song left with no such URL | `bridge/engine.ts`, `bridge/options.ts` |
| The codec per `canPlayType`, AAC on macOS before 15.4 | Opus 251 only where the engine says `probably`, which it never does on macOS before 15.4 | `bridge/engine.ts`, `src/environment.rs` |
| Re-resolving on a 403 or after about 5 hours | The stream lifecycle's status check, and a one-hour margin before URLs expire | `bridge/options.ts` |
| The URL cache follows the network | Native route changes, plus `online` and `offline` | `bridge/network.ts`, `src/network.rs` |
| A tray menu | Rust builds it; the player's state comes back through `set_now_playing` | `src/tray.rs`, `bridge/tray.ts` |
| Close to tray | The close button hides the window, to the tray where one shows (Windows, Linux) and to the Dock on macOS, leaving full screen first | `src/window.rs`, `src/fullscreen.rs` |
| Background throttling off | `backgroundThrottling: disabled` (macOS 14 and later), a Web Lock (Windows, Linux) | `tauri.conf.json`, `bridge/keep-awake.ts` |
| Media Session | The web app's, which each webview hands to the system's media controls | `@fxm/player` |

**`<audio src>` only for URLs that passed the probe.** The desktop app reads stream bytes through Rust, so the YouTube resolver (stage 1.4) fetches the last 64 KB of every file before it offers a URL: `fullLength` is `verified`, or `capped` for a URL that stops early, which never plays anywhere. `DesktopAudioEngine` (the direct audio engine with the desktop rules) also says `no` to an IP-bound URL that is still `unverified`, which happens when the probe got no answer. The player never hands the engine a stream it says `no` to, and the playback policy then takes the probed fallback rung (itag 18), then resolves again from the top. Free sources (Internet Archive, Jamendo) are not IP-bound, nothing caps them and nothing probes them, so they play as they are.

When no rung's probe answers, say on a flaky connection, the stream lifecycle finds nothing playable and rejects with `Unavailable` (`no-stream`), which the player's own classes skip at once. The desktop player retries it instead (`desktopClassifyFailure` in `bridge/options.ts`, part of `DESKTOP_PLAYER_OPTIONS`): after 0, 1 and 3 s, each time resolving the song afresh from the top rung, which probes again. A song still unplayable after those 3 retries is given up and counts toward the player's circuit breaker, which stops playback after 4 such songs in a row, as it does for network failures; the web app, which plays an unverified URL, would have played or retried it. The lifecycle takes such a retry for the user playing the song again, which matters only for a Suggest-band guess, and a resolution that held a guess back fails with `needs-review`, which is still skipped. Where the probe should get an answer more often is stage 1.4's to decide (its timeout and retries).

**The codec per `canPlayType`.** The playback policy plays Opus 251 only where the engine says `probably` for `audio/webm; codecs="opus"`, otherwise AAC 140 (`choosePlaybackStream`). WebKit plays Opus in WebM only from macOS 15.4, and a WKWebView's User-Agent says macOS 10.15.7 on every version, so the shell reports the real version (`desktop_environment`, from `NSProcessInfo`), and on earlier versions the engine rates Opus `maybe` at most, whatever WebKit answers: AAC plays whenever the song has it, and Opus remains the fallback. Until the shell has answered, a few milliseconds after start, only the probe rule applies. WebView2 answers `probably` for Opus, and so does WebKitGTK where GStreamer's base and good plugins are installed (AAC needs gst-libav).

**Re-resolving on a 403 or after about 5 hours.** An `<audio>` element never sees a status code, so after a playback failure the stream lifecycle asks the source for the URL's status with a ranged GET through Rust (`checkStatus`, stage 1.4): a 403 resolves the stream again, once on the same rung, then on the fallback, and a 403 on a cached URL also flushes the cache (a probable new IP address). YouTube's URLs expire about 6 hours after they were resolved, and the desktop app resolves them again once they are about 5 hours old (`DESKTOP_URL_REFRESH_MARGIN_MS`, one hour before `expire`, where the web app keeps 10 minutes): the URL cache stops handing them out, and the player refreshes a stream loaded that long ago, say before a long pause, before it plays again. The wider margin covers a long track that starts on an old URL, whose media element may ask for more bytes near its end, and a clock that is some minutes off.

**The network.** YouTube's URLs work only from the IP address that resolved them, so the stream lifecycle keys its cache by network. `src/network.rs` asks the operating system every 5 seconds which local address it would use to reach the internet, over IPv4 and IPv6, and tells the window (`fxm-network-change`) when either changes: a new Wi-Fi network, a cable, a VPN going up or down, a new temporary IPv6 address. Asking sends nothing: connecting a UDP socket only picks the route, and the destinations are documentation addresses (RFC 5737, RFC 3849). `createDesktopNetworkMonitor` turns that, plus the webview's `online` and `offline`, into the lifecycle's `NetworkMonitor`. It ignores the Network Information API, which only WebView2 has and whose estimates change on their own every few minutes.

**The tray.** Rust builds the tray icon (`src/tray.rs`), so it is there before the page loads and keeps working if the page hangs:

| Item | What it does |
|---|---|
| The current track and what the player does with it, or "Nothing playing" | Nothing, it informs; after an error, shows the window |
| Play / Pause | Plays or pauses: `fxm-media-action` with `toggle` |
| Next | The next track (`next`) |
| Previous | The previous track, or the start of this one after 3 s (`previous`) |
| Show FXM | Shows and focuses the window |
| Quit FXM | Quits |

The first line says what the player is doing, and the icon's tooltip says the same with the track (Windows and macOS; Linux status areas show no tooltips):

| The player | Menu | Tooltip |
|---|---|---|
| Nothing queued | Nothing playing | FXM |
| Playing, or loading the next track | Creep – Radiohead | FXM: Creep – Radiohead |
| Paused, stopped or not started | Paused · Creep – Radiohead | FXM: Paused · Creep – Radiohead |
| Stopped on an error the user must look at (a bot check, a login, too many failed tracks in a row) | Can't play: open FXM to see why | FXM: Can't play Creep – Radiohead |

The first line is disabled, so it only informs, except after an error: then choosing it shows the window, which says what went wrong. The media items are disabled while nothing is queued. A click on the icon shows the window on Windows; on macOS it opens the menu, as menu bar items do, and on Linux the status area always opens the menu. On macOS the icon is a template image of the FXM bars (`tray/36x36.png`), which macOS draws in the menu bar's own colour. Windows and Linux show an icon of their own (`tray/color/32x32.png`, from `assets/tray-color.svg`): the purple tile edge to edge with three bold bars, every edge on a 2 px grid, so it halves to a sharp 16 px, the notification area's size at 100% scaling. The app icon, drawn on the macOS icon grid with 3 px margins, shrank there to a 13 px tile whose five bars blurred into one.

`connectTray` (`bridge/tray.ts`) sends the player's state to `set_now_playing` whenever what the menu shows changes (`state`: `playing`, `paused` or `error`, with the title and artists), and runs the menu's media actions on the player. An update that fails is sent again, with the latest state, after 1 s, then 2, 4 and so on up to a minute while it keeps failing; updates wait for that retry, and the failure is reported once per run. Lone UTF-16 surrogates, such as a title cut in the middle of an emoji, become U+FFFD on the way (`wellFormed`): Rust's JSON parser refuses them, and every update for that track would fail. Rust caps what it shows (60 characters in the menu, 120 UTF-16 code units in the tooltip, which Windows cuts at 127) and doubles `&`, which menus read as a mnemonic marker; muda, Tauri's menu library, does the same for `_` in GTK menus. Whether the Windows tooltip drops a single `&` too is part of the [manual check](#manual-check).

Linux shows tray icons through an AppIndicator library (`libayatana-appindicator3` or `libappindicator3`), which tray-icon loads when the icon is built and panics without. FXM checks for it first, under the four names libappindicator-sys tries (the versioned `.so.1` files, then the unversioned `.so` that some AppImages bundle alone), and runs without a tray icon where none loads. The library alone shows nothing: a panel must host the icon, through the session bus's `org.kde.StatusNotifierWatcher`. KDE Plasma, Cinnamon, XFCE and most other panels do; GNOME does only with its AppIndicator extension. So at each close FXM also asks the watcher whether a host is registered (`IsStatusNotifierHostRegistered`, through gio), and quits rather than hides when none is or nothing answers within half a second. A panel that knows only the older XEmbed tray (i3bar, for one) may still show the icon through libappindicator's fallback, but FXM can't tell, so closing quits there too. The smoke build has no tray icon: it runs unattended and leaves the menu bar alone.

**The close button** (`close_action` in `src/window.rs`), whether or not music plays:

| | The close button, ⌘W, Alt+F4 |
|---|---|
| macOS | Hides the window; a window in full screen leaves full screen first |
| Windows, and Linux where a panel shows the tray icon | Hides the window to the tray; the first time, a notice says where FXM went and how to quit it |
| Linux without a tray icon (no AppIndicator library, or no panel that hosts it) | Quits |

On macOS FXM behaves like other Mac apps: closing the window leaves FXM in the Dock and the menu bar; clicking it in the Dock, Window > FXM (⌘0) or Show FXM in the menu bar brings the window back, and Quit (⌘Q) quits. Tauri's default app menu has no item for a hidden window, so `app_menu` adds Window > FXM, as Calendar has Window > Calendar; without it the keyboard could reach the window only through the Dock. A window in full screen first leaves it: hidden in full screen, it would leave its Space behind, empty and black, until the user swipes away (Electron apps meet the same, electron#20263). Tauri can't tell when the animation ends, since tao counts the window as windowed as soon as it is asked to leave, so `src/fullscreen.rs` waits for AppKit's `NSWindowDidExitFullScreenNotification` and hides the window then, unless the window was asked for again meanwhile or more than 5 s passed. It comes back, and FXM next opens, out of full screen.

On Windows and Linux FXM behaves like other tray apps: closing the window leaves FXM in the tray, playing or not, and Quit FXM in the tray menu quits. Windows puts a new app's icon in the overflow (the ^ next to the clock) until the user drags it onto the taskbar, so the music would play on with nothing in sight: the first time the window hides, a notice (a message box from tauri-plugin-dialog) says where FXM went and how to quit it, and `tray-notice-shown` in the app's config folder remembers that it did. Where the desktop shows no tray icon, closing quits, so FXM never lingers out of sight. Launching FXM again always brings the window back.

**Background playback.** A hidden window's page must keep running: the player moves to the next track, retries and watches for stalls on timers and events.

- **macOS:** `backgroundThrottling: disabled` on the window, which Tauri turns into WebKit's `inactiveSchedulingPolicy` none (macOS 14 and later). Without it, the smoke test's hidden page stopped while its muted track played (see [Live smoke test](#live-smoke-test)).
- **Windows and Linux:** Tauri has no such switch for WebView2 or WebKitGTK, and its documentation suggests a pending Web Lock. `keepAwakeWhilePlaying` (`bridge/keep-awake.ts`) holds a shared Web Lock, `fxm-background-playback`, while the player is playing or loading the next track, and releases it on pause, so an idle FXM in the tray is throttled as usual. Chromium, and so WebView2, never freezes a page that holds a Web Lock; whether the lock also spares it the intensive throttling of timers that starts after 5 minutes hidden is what the smoke test's 9-minute playlist shows on WebView2, and the player moves between tracks on media events, which that throttling leaves alone. Whether WebKitGTK gains anything from the lock is part of the [manual check](#windows-and-linux). The lock is held on macOS too, where it costs nothing. macOS 11 to 13 have no inactive scheduling policy: there, playback relies on WebKit keeping a page that plays audio running, and whether the lock adds anything is untested.

The webviews allow audio to start without a user gesture (wry's default), so tracks follow one another while the window is hidden.

**Media Session and media keys.** The web app connects its player to the Media Session (`connectMediaSession`, stage 2.2), and each webview hands that to the system:

| | Media controls | Notes |
|---|---|---|
| macOS (WKWebView) | Now Playing in Control Center, media keys | Measured in a WKWebView harness by the research, and the smoke test checks the Media Session's titles |
| Windows (WebView2) | The media flyout, the lock screen, media keys | The flyout names the app "Unknown app": the Media Session belongs to WebView2's browser process (`msedgewebview2.exe`), not to FXM, an open WebView2 bug ([WebView2Feedback#2236](https://github.com/MicrosoftEdge/WebView2Feedback/issues/2236)). The controls, the title and the artwork work; only the app's name is wrong. Fixing it would take FXM's own System Media Transport Controls from Rust, with WebView2's own media keys turned off: not done |
| Linux (WebKitGTK) | MPRIS (desktop media widgets, `playerctl`), where WebKitGTK is built with the Media Session | Part of the manual check; the tray works either way |

**Capabilities.** The web app's capability grants Tauri's `core:default` minus `core:tray:default` and `core:menu:default`, so page script can neither change the tray nor add tray icons or menus of its own. `set_now_playing` and `desktop_environment` join the app's commands, each behind a permission, for the main window only. The page's text in the tray is untrusted input to Rust: it arrives through a struct that refuses unknown fields and states, and Rust drops control characters and caps its length.

## Content security policy

```
default-src 'self'; img-src 'self' https: data: blob:; media-src 'self' https: blob:;
connect-src ipc: http://ipc.localhost 'self'; script-src 'self' 'wasm-unsafe-eval';
style-src 'self' 'unsafe-inline'
```

- `connect-src` has no `https:`: page script reaches the network only through Tauri's IPC (`ipc:` on macOS and Linux, `http://ipc.localhost` on Windows), so every request goes through Rust, with its scope and header policy. A stray `fetch()` from page script is blocked instead of going out with the webview's origin and cookies.
- `media-src https:` lets `<audio>` play googlevideo URLs directly, as well as Internet Archive's and Jamendo's media hosts and a user's Invidious instance, whose hosts can't be listed at build time. The page can't read those responses.
- At build time Tauri adds the SHA-256 hash of every inline script to `script-src`, so the theme script in `apps/web/index.html` keeps running.
- **No `'unsafe-eval'`.** The app's policy has none, and stage 7.2 added none: YouTube deciphering runs in a separate, hidden evaluator webview with a policy of its own (stage 1.11). Only if that webview can't work may 1.11 add `'unsafe-eval'` here, with the reason recorded in this README.

## Live smoke test

Stage 7.2 is done when, in a hidden window on macOS, Windows and Linux, a YouTube Music search succeeds, a VISIONOS URL resolved through the HTTP plugin passes the end-of-file probe, and that track plays to the end. Stage 7.3 is done when three consecutive full tracks play with the window hidden on each OS, including WebView2 and WebKitGTK. The smoke test checks both, through the app's real networking and player:

```sh
scripts/run.sh pnpm --filter @fxm/desktop smoke
```

- It builds a debug version of the app (`smoke:build`) with the `smoke` feature, whose `src/smoke.rs` prints the page's progress and report and exits, and with `tauri.smoke.conf.json` merged over the config. That file changes only the identifier (`io.github.pratyayops.fxm.smoke`, so the test never touches the app's data), the page (`smoke/`, instead of the web app) and the window: hidden, and never suspended. Release builds never turn the feature on. The smoke build leaves out the tray and the single-instance plugin: runs from different checkouts share the identifier and may overlap on one machine, and the plugin would hand the second run over to the first one's app, which would show its hidden window.
- Then `smoke/run.mjs` runs it and prints a line per step. The exit code is 0 when no step failed; steps waiting for a stage that hasn't merged don't count as failures. It stops the app after 45 minutes without a report (`FXM_SMOKE_TIMEOUT_MS`).
- Stage 7.2's steps (`smoke/steps.ts`): the platform reports native networking; `sw.js_data`, where the YouTube provider gets its server-issued visitorData, is readable; Spotify answers (its server time, which needs no token); a YouTube Music search; a VISIONOS URL whose end-of-file probe passed; that track playing to its end; then the same probe and playback for a 27-second public-domain recording on Internet Archive, whose download URL redirects within the scope.
- Stage 7.3's steps (`smoke/playback-steps.ts`): where the app runs (the OS and webview versions, `canPlayType` for Opus and AAC and so the YouTube format the app plays, the Media Session and Web Locks); three YouTube Music songs played to the end one after another; three public-domain recordings on Internet Archive played the same way (`smoke/playlists.ts`: three Chopin waltzes from Musopen's recordings of his complete works, which Musopen released under CC0; 185.5, 184.2 and 175.8 s). Each playlist goes through the app's player, stream lifecycle and desktop bridge, connected as the web app connects them (`smoke/queue-player.ts`), and passes when every track ends on its own, the Web Lock is held while music plays and the Media Session shows each title. The report also says when each track started, counted from when the page loaded: in the hidden window, how long the page had been hidden. The page notes a start when it next gets to run, so on a busy machine the times run late, never early.
- Playback is muted, which makes the hidden page's case harder: a page that plays nothing audible is the first to be throttled.
- **Past five minutes.** Chromium, and so WebView2, throttles a hidden page's timers hardest (intensive wake-up throttling) once the page has been hidden for 5 minutes and silent for 30 seconds, and muted audio is silent. The free playlist plays for 9 minutes, longest first, so even with nothing before it the second waltz ends, and the third starts, past the 5-minute mark: on WebView2, a run whose last track started after 5:00 shows a change of track and a whole track under that throttling. The first runs below played a playlist of 2 minutes, which ended before it.
- It sends 3 requests to YouTube (a few more once the resolves run), 1 to Spotify and a few to Internet Archive, plus the tracks' own. Run it from a residential connection: YouTube's bot checks single out datacenter addresses.

**The swap.** Stages 1.3 (the YouTube Music provider) and 1.4 (the stream resolver) had not merged when 7.2 and 7.3 were built. `smoke/youtube.ts` and `youtubeSongs` in `smoke/playlists.ts` are the only places the test touches them: until then, the search is one plain InnerTube call in the CORS-simple shape, and the resolves and the three songs wait. Their comments show the few lines that put the real providers in their place.

## Manual check

The tray, the close button, the system's media controls and the Web Lock behave differently on each OS, and only macOS was at hand when stage 7.3 was built, where the smoke test covers playback in a hidden window but not the tray, which its build leaves out. The unit tests cover the logic (`close_action`, the tray's text, the bridge); what the systems do needs a person at each machine. The steps with songs need a web app that plays them, once stages 1.4, 2.4 and 2.5 have merged; until then, check the rest. Record each run in the [results](#results-of-the-manual-check).

### macOS

Build the app (`make desktop-build`) and open `FXM.app`:

- The FXM bars appear in the menu bar, black on a light menu bar and white on a dark one (switch in System Settings > Appearance). Their menu shows "Nothing playing", Play, Next and Previous disabled, Show FXM and Quit FXM. With VoiceOver on (⌘F5), moving to the bars reads them as FXM, and it reads each item of their menu.
- Play an album: the menu shows the song and Pause, and paused, its first line starts with "Paused ·". Now Playing in Control Center shows the song with its artwork, and its buttons and the media keys play, pause and skip.
- Play a song whose title or artist has an `&` and one with an `_`, such as "Mrs. Robinson" by Simon & Garfunkel: the menu shows both characters as they are.
- Close the window with the red button, then again with ⌘W: the window disappears each time, FXM stays in the Dock and the menu bar, and the music goes on. Each of these brings the window back: clicking FXM in the Dock; Window > FXM (⌘0) once FXM is the active app (⌘Tab to it); Show FXM in the menu bar's menu.
- Enter full screen (View > Enter Full Screen, or ⌃⌘F), then press ⌘W: the window leaves full screen, then disappears, and you land on the desktop, not in an empty black Space. Click FXM in the Dock: the window comes back, out of full screen. Do the same with the red button, which shows in full screen when the pointer is at the top of the screen.
- Quit with ⌘Q, and once more with Quit FXM in the menu bar's menu: FXM quits each time, and opens again with its window where it was.

## Maintenance

**Icons.** Edit `assets/icon.svg`, then run `scripts/run.sh pnpm --filter @fxm/desktop icons` from the repo root. The tray icons have sources of their own: `assets/tray-template.svg` for the macOS menu bar, the bars alone in black on a 36 px canvas (18 pt at 2x), and `assets/tray-color.svg` for Windows and Linux, the tile edge to edge on a 32 px canvas, every edge on a 2 px grid so it halves cleanly to 16 px. Run `scripts/run.sh pnpm --filter @fxm/desktop tray-icon` after editing either. The mark sits on the macOS icon grid (an 824 px body on a 1024 px canvas), so it lines up with other apps in the Dock. `tauri icon` writes the entries of `icon.icns` in a different order on every run, so that file shows up as changed even when the art didn't.

**Versions.** Every pin follows the repo's 14-day rule (see [DEVELOPMENT.md](../../docs/DEVELOPMENT.md)):

| What | Pinned in | Notes |
|---|---|---|
| Rust | `src-tauri/rust-toolchain.toml` | 1.98.1. 1.99.0 miscompiles FFI `bool` returns on x86_64 ([rust-lang/rust#163911](https://github.com/rust-lang/rust/issues/163911)), and the fixed 1.99.1 is too new |
| rustup | `scripts/install-rust.sh` | Version plus one SHA-256 per platform, from `https://static.rust-lang.org/rustup/archive/<version>/<target>/rustup-init.sha256` |
| Crates | `src-tauri/Cargo.lock` | See below |
| `@tauri-apps/cli`, `@tauri-apps/api` | `package.json` | pnpm's `minimumReleaseAge` applies. Keep `@tauri-apps/api` on the same minor version as the `tauri` crate: `tauri build` refuses mismatched versions |
| `@tauri-apps/plugin-http` | `packages/platform/package.json` | The same minor version as the `tauri-plugin-http` crate (2.8), for the same reason |

Cargo has no stable equivalent of pnpm's `minimumReleaseAge`, so re-resolve the whole lockfile with a publish-date cutoff 14 days back:

```sh
cd apps/desktop/src-tauri
cutoff=$(node -p 'new Date(Date.now() - 14 * 864e5).toISOString().slice(0, 19) + "Z"')
RUSTC_BOOTSTRAP=1 ../../../scripts/run.sh cargo generate-lockfile -Zunstable-options --publish-time "$cutoff"
```

`RUSTC_BOOTSTRAP=1` unlocks Cargo's unstable `--publish-time` flag for this one command, which only resolves versions and compiles nothing. Builds always use `--locked` in CI.
