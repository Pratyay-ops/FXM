# Downloads in the web app

The web app's side of stages 4.1 and 4.2: where downloads are stored, which tab runs the queue, the UI, offline playback, and "Save to device" in the format the user picks. The queue itself is [`@fxm/downloads`](../../../../../packages/downloads/README.md), the conversion [`@fxm/convert`](../../../../../packages/convert/README.md).

| File | What it holds |
|---|---|
| `runtime.ts` | The app's downloads, created on first use (`getDownloads`): the manager over the `fxm-downloads` database and the Origin Private File System (in the Android app, the app's own storage), the Downloads playlist kept in step, `startDownloads` (the tab with the Web Lock runs the queue; in the Android app, with the background service), `getOfflineStore` for the player, `resetDownloads` for tests |
| `download-db.ts` | The `fxm-downloads` IndexedDB database (Dexie) and the `DownloadStore` on it |
| `opfs/` | The `DownloadStorage` on the Origin Private File System: `storage.ts` on the page, `worker.ts` and `handler.ts` in a dedicated worker that writes through sync access handles, `protocol.ts` for their messages |
| `environment.ts` | Where downloads meet the rest of FXM: the environment the app's composition root connects (`connectDownloadEnvironment`: the platform's context at the request budget's `bulk` priority, and the resolver over the stream lifecycle's own sources, matching engine and match cache), and the stand-in until then |
| `persistence.ts` | `navigator.storage.estimate()`, `persisted()` and `persist()` for the usage meter |
| `hooks.ts` | Live reads of the downloads, availability per track, storage numbers |

## Storage

- **Files** live in the `downloads` folder of the **Origin Private File System**. A dedicated worker writes them through `FileSystemSyncAccessHandle`s: writes land in the file in place, and a flushed write survives a crash, so a download continues where its file ends. Pages list and read files themselves, and play a complete one from a `blob:` URL typed with its media type (only audio, MP4 or WebM video, or plain bytes: never a type a browser would render as a page). File names other than 1 to 64 letters, digits, `-` and `_` are refused on the page and in the worker.
- **Support** is tried, not assumed: on first use the page opens the downloads folder and asks the worker whether it has sync access handles (`probe`). Until that answers, nothing is offered; browsers without OPFS, workers or sync access handles (an older Safari), and private windows that refuse the folder, get no download offers, and the Downloads tab says why.
- **A worker that fails or hangs** (its script gone after an update, a crash, no answer for 30 s) is terminated: the requests waiting for it fail the download as `storage` ("Reload FXM and try again") instead of hanging, and the next request starts a fresh worker.
- **Room for the library.** Downloads share the browser's quota with the library, so a download that would leave less than the smaller of 10 % of the quota and 200 MB for the rest of FXM fails as `storage-full` (checked when a file opens and every 8 MiB written), and the queue pauses before the library's own writes can fail.
- **Records** live in their own IndexedDB database, `fxm-downloads`, apart from the library's `fxm`: downloads describe files on this device, so they stay out of library backups. The Downloads playlist (in the library, stage 2.6) holds their order.
- **Persistence.** The first download asks the browser to keep FXM's data when space runs low (`navigator.storage.persist()`), from the click, where Firefox can ask the user and Chromium decides by itself. The Downloads tab shows whether it agreed, with a button to ask again, and a usage meter: what downloads take, what the rest of FXM takes, and what is free for FXM (`navigator.storage.estimate()`).

## In the Android app

Stage 6.4. Where the `FxmDownloads` plugin is on the Capacitor bridge, the app's downloads use it ([`@fxm/downloads`' native side](../../../../../packages/downloads/src/native/README.md), [the Android module](../../../../../apps/mobile/android/fxm-downloads/README.md)); the queue, its records and the UI stay the same:

- **Files** live in the app's own storage, not in the browser's. Support is tried the same way (the plugin's `info`), and the storage card shows the room left for downloads on the phone (what Android's low-storage reserve leaves free) instead of the browser's quota, and says that FXM keeps the downloads: the system never deletes them for space, so there is no "Keep my downloads".
- **In the background.** `startDownloads` reports the queue to the app whenever it changes (`connectBackgroundDownloads`), and a `dataSync` foreground service with a progress notification keeps the app, and the queue in its page, running while it has work, also with the screen off. On Android 13 and later the first download asks once to show notifications (`NOTIFICATIONS_ASKED_KEY` remembers it); refused, downloads run all the same.
- **Save to Music folder.** Track lists offer it for finished downloads, instead of Save to device… (below): a copy in Music/FXM, where every music app finds it, named `Artist - Title`. A download of a video file (YouTube's itag 18) says it can't be saved yet: its audio must be taken out first (stage 4.2).
- **Offline playback** uses the same offline store; the playback URL of a file is the WebView URL Capacitor serves it at, which the native player (Media3) plays from the device.

The composition root's environment and queue (`src/app/services/downloads.ts`, stage 2.9b) are the same there: the app's platform fetches through Android's native HTTP, which reads YouTube's bytes (`mediaBytes`), so YouTube songs download in the app too, from URLs that passed the end-of-file probe and are resolved again once they expire, and the queue starts once the tier is known.

## One tab runs the queue

The app's composition root calls `startDownloads()` once its environment is connected and the tier is known (`startAppDownloads` in `src/app/services/downloads.ts`: after FXM Connect answered, or its grace period ended), loaded lazily, so Dexie and the manager stay out of the entry chunk. A queue that started earlier would meet the Free tier while FXM Connect wakes up, and fail every YouTube download it resumed as one that can't be downloaded here. Once the storage is known to work, it asks for the `fxm-downloads` Web Lock, which one tab holds at a time; that tab fetches and writes. Every tab can queue, pause, resume and delete downloads: those are changes to records, which Dexie broadcasts, and the running tab reacts. When it closes, the next tab gets the lock and continues where the files end. A browser without Web Locks runs the queue in every tab.

The running tab hears only about changes the queue cares about: its subscription reads the status index for unfinished downloads and reacts when that changes, never to a progress save, and each pass reads only the unfinished downloads. The lists read the completed downloads apart from the unfinished ones, menus read only the status index, and the storage meter asks the browser at most every 5 s while downloads run, so thousands of downloads cost nothing while one runs.

The running tab also keeps the **Downloads playlist** in step: a completed download is added to the top, and deleted ones leave it together (`addDownload`, `removeDownloads` from the library repository). When it starts, it adds completed downloads the playlist lacks. Commands on many downloads ("Download all", "Remove all downloads", a selection) are one change to the downloads and one to the playlist.

## Offline playback

`getOfflineStore()` is the `offline` option of the player's `StreamLifecycle` (stage 2.3): the app's composition root asks it first (`src/app/services/offline.ts`, before the user's own files tagged with the track's ISRC), so the playback policy plays a downloaded track from the device before resolving anything, also without a network (once the app itself is loaded; the offline app shell is stage 5.1).

A downloaded track plays at the loudness its stream had (stage 8.1): the record keeps the stream's `loudness` (YouTube's `loudnessDb`), and when the stream said none, the runtime reads the finished file's own ReplayGain or R128 tags into the record (`attachFileLoudness` in `features/audio-effects/download-loudness.ts`).

## UI

- **The Downloads tab** of the library shows, above the playlist in its custom order: a notice when the browser can't store downloads, or when YouTube songs can't be downloaded here (no FXM Connect, the Lite tier included); the storage card with the usage meter, persistence and "Remove all downloads"; the downloads on their way with a progress bar, a pause/resume/retry button and a cancel button each, and "Pause all"/"Resume all"; and songs in the playlist that aren't downloaded on this device (after restoring a backup from another device), to download or remove.
- **Track lists** (playlists, Liked songs, Downloads) have "Download", "Cancel download" or "Remove download" in each song's menu, and "Download" for a selection. In Downloads, "Remove download" is the only way out of the list. A playlist's menu has "Download all".
- **The catalog pages** (search, album, artist and playlist pages, stage 2.4) have "Download" in their menus: the composition root sets 2.4's `DownloadActions` to the downloads' own action, which says what became of the click.
- **`DownloadButton`** sits beside the like button on Now playing (stage 2.5).

Downloads keep the source's own file, which plays offline as it is; a copy in another format is what Save to device saves (below, stage 4.2, on with `RELEASED.conversions`, which Settings follows). Nothing is offered where the bytes are unreadable (YouTube audio needs FXM Connect, and later the desktop app or the Android app, and never the Lite tier), nor what the app can't resolve (before the composition root connected its environment, nothing). A download the manager paused on its own says why in its row ("Paused · There is no room left for downloads", or after a YouTube bot check).

## Save to device

A downloaded song's menu (in playlists, Liked songs and Downloads) has **Save to device…**, except in the Android app for now (below). Its dialog lists every format with its honest label from `@fxm/convert` (`exportChoices`): "Original (Opus)", "FLAC (converted from Opus, same quality as the source)", "MP3 (converted from Opus, some quality loss)", and so on; YouTube audio is never called lossless, and choosing a lossless format for it says that converting gives a bigger file, not a better one. The choice starts at the download format of Settings → Audio quality, and MP3 takes its bitrate from there. With `RELEASED.conversions` off, the dialog offers the original alone, as Settings does.

Save works in two steps. Straight from the click, the device saver asks where to save (the browser's save picker in Chromium on desktop; elsewhere the file goes to the browser's downloads), because browsers open their picker only from a click. Then FXM reads the stored file, fetches the cover (the track's largest artwork, through the download environment's platform `fetch`; WebP becomes JPEG through a canvas) and the lyrics (LRCLIB), each left out after 8 s or on any failure, converts and tags the file in the conversion worker, and writes it. The dialog shows the progress and a Cancel button, which stops the worker; closing the dialog cancels too, and nothing changes on it afterwards. A save that fails or is cancelled gives up the place it picked, so no empty file stays in the user's folder. Failures say what to do, in words that fit the chosen format: the core can't load here (save the original instead, said only when another format was chosen), the file is damaged or gone (download it again), the downloads' storage can't be read right now (reload), the browser ran out of memory, the folder refused the file, or the device couldn't ask where to save. A stored file FXM can't read at all (a video whose audio isn't AAC in MP4) gets a notice instead of the formats. The stored download stays the original either way, for offline playback.

The conversion worker loads FXM's ffmpeg core from the app's `ffmpeg/` folder on the first save that needs it (the deploy puts it there; `make dev` serves a local build from `make ffmpeg-wasm`, tools/ffmpeg-wasm/README.md), and the service worker keeps it for offline saves (`pwa/options.ts`). Saving an original MP3, FLAC, Ogg or WAV, or an M4A as M4A, needs no core: FXM's own writers tag those. An original WebM (YouTube's usual audio) gets its tags from the core, and where the core can't load is saved as it is, untagged, which the confirmation says ("without its tags").

The desktop app (7.4) and the Android app are to save natively: they pass their own `DeviceSaver` to `setDeviceSaver` (a save dialog, the device's music library), and the rest of Save to device stays as it is. Stage 6.4 didn't give the Android app one, and the browser's saver can't save there: the WebView drops its download (Capacitor gives it no download listener), so the copy would go nowhere while the dialog said it was saved. So the Android app's track lists leave Save to device… out for now (`useSaveMenuItem` in `menu.ts`), and the stage that gives the app its saver offers the entry there again; for anything but the original, that saver also needs the ffmpeg core in the APK, which `build:mobile` doesn't copy. Meanwhile, "Save to Music folder" (above) keeps a copy of the original file.

## Testing

`setupDownloads()` from `testing.ts` gives the app's downloads an in-memory storage, a `FakeMediaServer` as the network and a `FakeDownloadResolver`, for a tier the test picks, and runs the queue; with `android: true` the files go to a fake `FxmDownloads` plugin instead (`android.test.tsx`: the app's storage, the background reports, the notification question, Save to Music and no Save to device, the storage card). The test setup resets everything after each test. OPFS is tested against `opfs/fake-opfs.ts`, with the worker's handler run in-process and through a fake worker. Save to device is tested with `createInProcessConverter` from `@fxm/convert/testing` (the whole pipeline on a fake core, or on a core that never loads, without the worker), a converter that runs until it is cancelled, a fake device saver and a fake lyrics provider, so nothing reaches the network. A cover is fetched once through a real platform transport over a fake `fetch`, which checks that the host table lets YouTube Music's and Spotify's cover hosts through. In a real browser, `e2e/save.spec.ts` downloads a song from Internet Archive through the app's composition and saves it as FLAC with the real ffmpeg core (skipped where none is built), also against `make dist` under its real headers ([the app's README](../../../README.md)).
