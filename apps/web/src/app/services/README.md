# The composition root (stages 2.9 and 2.9b)

The one place where the web app builds the real pieces of the earlier stages and plugs them into the seams its pages use. Stages 2.3 to 2.6, and the stages after them, were built in parallel against fakes behind small adapters; this folder is what replaces the fakes. Stage 2.9 built it; stage 2.9b plugged in the stages that merged after it (Home, imports, downloads, the embed, the signed YouTube config, the matching config, scrobbling, the desktop app's playback, local files, the browse links and the library's play buttons). Everything runs on the user's device: FXM has no servers.

**The first render waits for nothing.** `main.tsx` renders the shell at once and loads this folder beside it, in a chunk of its own (`import('./app/services')`, then `startAppServices()`), so the app's first bundle carries none of the platform, the stream lifecycle, the providers, the library or local files (on 2026-10-26, with stage 2.9b's wiring, in the production build: the first bundle 442 KB, 140 KB gzipped, with the app's player and the shell; this folder's chunk 28 KB, 10 KB gzipped). The pages follow the sources registry as the platform detects the tier and the providers register.

**The app's player** is stage 2.5's (`features/now-playing/playback.ts`), created with the first render, which the player bars, Now playing, the queue and the system media controls show, and which records each play as a listening signal (stage 3.1). It plays through `createAppPolicy()` (`features/now-playing/playback-policy.ts`), which follows whichever policy is connected and makes what the player asks before then wait for it. `startAppServices()` connects this folder's `policy` (with local files in front, `withLocalFilesFirst` from stage 4.4, so they never reach the lifecycle) and the player (`connectPlayer`) first: the policy's resolver waits for the platform itself, so the play buttons work while FXM Connect answers. Where the services don't run (the development fake catalog) or can't start, it connects the stand-in instead (`createPendingPolicy()`), which plays local files only and stops on anything else with a reason rather than wait.

**Stage 2.7's seams** are wired in `index.ts` too: when YouTube's code has loaded (`onYouTube`), the kill switches of the YouTube config in use become the app platform's (`setKillSwitchSource`, and `recheckConnection()` whenever the Lite switch changes, also when a newer signed config arrives), and its stream ladder the Diagnostics self-test's resolver (`setSongResolver`), unless the development fake mode set one first. `getAppPlatform()` creates the platform with `reportLoginRequired: false`, as the services did theirs: the ladder reports the bot checks it tells apart from age gates itself.

**The features that need the platform itself** are plugged in once it is ready (`connectFeatures` in `index.ts`): Home's recommendations and catalog (`home.ts`, `appHomeServices`), which autoplay's radio uses too (stage 3.4), the downloads' environment, the catalog's Download entries and the download queue (`downloads.ts`, `connectDownloadEnvironment`, `startAppDownloads`), and the context lyrics, SponsorBlock and scrobbling send their requests with (`connectAppContext`, `lib/app-context.ts`). Imports connect at once (`imports.ts`, `connectAppImportServices`) and wait for the platform themselves. Home gets the registry and the player at once too, with the tier unknown (`detecting`) until the platform's first detection has ended (`homeSourcesUntil`, `tierKnown`): FXM Connect's answer, and where it gives no full access the first Lite self-test, which the platform doesn't wait for itself, 4 s at most. Meanwhile Home shows a placeholder, never the Free tier's install pitch. Home's development fakes (`?fake-home=`) keep Home to themselves. `stopAppServices()` takes each of them back.

**The download queue** (stage 4.1's `startDownloads`, which one tab runs at a time) starts once the downloads' environment is connected and the tier is known: the registry no longer says `detecting`, so FXM Connect has answered, or its grace period ended (`startAppDownloads`). A queue that started earlier, while FXM Connect's service worker woke up, would meet the Free tier and fail every YouTube download it resumed (the rest of a "Download all" after the tab was closed) as one that can't be downloaded here. The runtime's code loads at once, so a Download click finds it there.

**While FXM Connect answers** (`connecting.ts`): its content script marks `<html>` before FXM's code runs, but answers the ping only once its service worker is up, which can take a second or two. So `main.tsx` calls `markConnecting(appSources)` before the first render: while the marker is on the page, the registry's snapshot says `detecting`, and the pages show "Connecting to FXM Connect…" instead of the Free tier's install pitch. The composition root ends that as soon as FXM Connect answers, even after the platform's 800 ms wait (its client still hears a late answer), and the grace period of 5 s at the latest: an FXM Connect that never answers is as good as none. Home waits longer, for the first Lite self-test too (above); search doesn't yet, so during a slow first Lite check it says "Search needs YouTube Music access" until Lite passes.

**Lazy loading.** YouTube (`@fxm/sources/youtube` with its module host: one chunk of 91 KB, 31 KB gzipped, on 2026-10-26), Spotify, Internet Archive, Jamendo, MusicBrainz, LRCLIB, the matching engine, Home's recommendation sources and the signed updates' updater (56 KB, 22 KB gzipped, with its signature checks) are each imported the first time something needs them (`lazy-provider.ts`). youtubei.js (663 KB, 166 KB gzipped) comes with the session's first InnerTube call, and the advanced rungs' player script, which the module host brings, imports it only when it extracts a player's functions (those rungs ship switched off); YouTube's chunk loads only where YouTube can be reached. The sources registry still lists them at once: a lazy provider has the members of the real one and loads it on its first call. YouTube's providers start loading in the background as soon as the platform reaches YouTube, so the first search doesn't wait for their chunk. A load that fails is tried again next time, and its error says what helps:

- a chunk that didn't download while the browser is offline is a `Network` error: "Couldn't reach …" with "Try again";
- one that didn't download while online is an `AppUpdatedError` (`lib/app-update.ts`): the build names its files after their content, so a tab opened before a deploy asks for files that are gone. The pages say "FXM was updated. Reload to get the new version." with a Reload button, and never reload by themselves, which would stop the music;
- an error while building a provider is a bug: it passes on as it is and is logged, rather than posing as a network problem with a "Try again" that can never work.

**The device's state.** The YouTube session's server-issued visitorData and the stream ladder's rung health live in IndexedDB, in a database of their own (`fxm-device`, `device-store.ts`), so a reload keeps the session and a rung that keeps failing on this IP address stays cooled down. Both outlive a switch of YouTube module or config. They belong to this browser, so library backups don't carry them. Without IndexedDB (some private windows), they stay in memory for the session.

**Signed updates** (`updates.ts`, stage 1.13). Once YouTube's code has loaded, `keepYouTubeCurrent` (loaded then, `keepYouTubeCurrentLater` in `youtube.ts`, so neither the services' chunk nor the embed's first one carries the updater) restores the last good signed config from IndexedDB (`fxm-updates`) and checks for a newer one, verified against the keys compiled into the build (`update-keys.json`). In a browser the config comes from the app's own origin (`<origin>/updates/`, with the page's `fetch`) and no code ever does: the web app's policy has no `blob:` in `script-src`, and it gets new code by redeploy. The desktop and Android apps also take the resolver module, from FXM's site (`DEFAULT_UPDATE_BASE_URLS`) through their native HTTP; their HTTP scopes must list `fxmusic.pages.dev/updates/` for that, until which they keep the copies they ship with. The providers are the host's live ones, so a newer config or module applies from the next call; its kill switches reach the platform (`YouTube.killSwitches()`, `subscribe`). Before the owner publishes a signed config, the site answers 404 and the app keeps its own.

**The request budget.** The platform's transport draws one slot for every InnerTube call, at the priority of the context it came from: `interactive` for what the pages ask, `current-track` and `prefetch` for the player, as the lifecycle sets them. The stream ladder therefore takes no slot of its own (`platformStreamBudget`); it reports the `LOGIN_REQUIRED` bot checks it tells apart from age gates, and the platform is created with `reportLoginRequired: false`, so each counts once. The transport reports HTTP 429 itself. Errors of the metadata providers and of the matcher's searches go to `platform.report`, so a bot check one of them noticed pauses bulk work too.

**Tiers.** The platform decides: Full with FXM Connect, and in the desktop and Android apps through their native HTTP (stages 7.2 and 6.2), Lite with the sandbox documents of stage 1.10 where the self-test passes and the kill switch allows it, Free only otherwise. The platform is the app's one, `getAppPlatform()` from stage 2.7 (`features/connect/app-platform.ts`), which its connection store, notices and Diagnostics follow too: `index.ts` passes it as `createPlatform`, so the pages and the onboarding never disagree about the tier, and every call counts in one request budget. Pages read the tier from the sources registry, and every provider call gets a context with the current capabilities, so nothing here branches on the tier, with one exception: **Spotify** is registered only where its anonymous token's TOTP secret can be fetched. Its hosts are outside the platform's table: the desktop and Android apps reach them directly, and a browser through the sandbox's user-host document (1.10), which the app's platform always has there. `index.ts` hands the secret's hosts (`SPOTIFY_SECRET_SOURCE_HOSTS`, known once Spotify's code has loaded) to the platform (`setAppUserHosts`), so they are routed there. In a browser the provider reads the secret through that document itself, the services' own or, as in the app, the platform's (`secretFetchFor` in `features/spotify-account/secret-fetch.ts`, which the account feature shares; `make dev`, which doesn't serve the document, fetches it directly). Spotify is then on wherever FXM Connect makes it reachable and the switch is on; in Lite and Free it can't be reached, and the pages don't offer it. A build whose platform had no user-host document (`reachesUserHosts: false`) registers no Spotify: the search page then has no Spotify chip, a Spotify link says "This version of FXM can't read Spotify yet", and the matching engine asks MusicBrainz's exact path for a Spotify track's ISRC instead.

| | Free | Lite (1.10) | Full |
|---|---|---|---|
| YouTube Music search and pages | Onboarding instead, with "Search Internet Archive instead" | Through the sandbox | Through the page |
| YouTube playback | Stops, with "needs FXM Connect" | VISIONOS, unprobed: the media element's first request is the probe, and the ladder hears which rung played | VISIONOS with the end-of-file probe, then itag 18 |
| Spotify | Not offered | Not offered | While its switch is on: its secret through 1.10's user-host document in a browser, natively in the desktop and Android apps |
| Downloads | Internet Archive and Jamendo | The same: YouTube's bytes can't be read | Every track, YouTube songs included |
| Home's recommendations | None: the user's own shelves | YouTube Music radio, ListenBrainz | Also Spotify (when on) and Last.fm's stations |
| Internet Archive | Yes | Yes | Yes |
| Jamendo | When a `client_id` is configured | The same | The same |

**Language and region.** The pages' provider calls and the services' (the lifecycle, the ladder, the matcher) take their context from one place, the sources registry, so search and playback ask YouTube alike: no `hl` or `gl`, which leaves YouTube's default language, the one whose labels the matching engine bundles, and the region of the IP address that streams play from. A region the user picks in Settings would be passed there, for both.

**The ladder hears which URL played** (`reportPlaybackStarts`): on the media element's first `playing` event, which the player reports as `playing` without `buffering`. The player says `playing` with `buffering` as soon as it asks the engine to play, before a byte arrived, so that alone never counts a rung as working.

**Jamendo** needs a `client_id`. The public one comes from the build (`VITE_FXM_JAMENDO_CLIENT_ID`, read by `src/lib/free-sources.ts`); without it Jamendo isn't offered, since its API refuses every call, and the app's copy names Internet Archive alone (`freeSources()`). Whether one ID may be shared by every user is open, so the deploy sets it only once the owner has confirmed it ([the Jamendo README](../../../../../packages/sources/src/jamendo/README.md#turning-jamendo-on-owner)).

**The Auto band** of the matching engine stays off: every match runs with `matchingOptions` from `@fxm/core` (the matching config's thresholds and measured fallback), whose Auto applies only where the config makes the band available (`isAutoMatchAvailable()`, false until stage 1.12's held-out report allows it) and the user's setting is on. Settings shows the switch only then (`AutoMatchSetting`). Matches are best guesses that play after a tap and wait for review; the band the lifecycle hands to `mayPlayMatch` is the best candidate's verdict under the setting (`effectiveMatchBand`), also for what the match cache read back. Imports match the same way (`matchRow` in `@fxm/sources/import`).

**The desktop app** (stage 7.3): `main.tsx` calls `setUpDesktopPlayback()` (`desktop.ts`) before the first render. Inside Tauri it loads `@fxm/desktop/bridge`, builds the app's player with `DesktopAudioEngine` (with the equalizer's readability rule of stage 8.1, `appEngineOptions()`: the user's files and the free sources go through Web Audio, googlevideo doesn't until stage 7.6) and `DESKTOP_PLAYER_OPTIONS`, connects the tray and the Web Lock, and hands the lifecycle its one-hour URL margin and the native network monitor (`startAppServices({ desktop })`). In a browser it does nothing and the bridge is never downloaded. Then `connectDesktopNotices()` (stage 7.5) connects the third-party notices that every desktop release carries to Settings → About (`features/settings/bundled-notices.ts`), which reads them through the bridge's `readThirdPartyNotices` when the user opens them; in a browser About links the site's notices instead.

**The Android app's update check** (stage 6.6, `features/app-update`) needs nothing from this folder, and stays out of it on purpose. It asks only GitHub's API, which isn't in the platform's host table either, so like sync it sends its one request with the WebView's own `fetch`, and it uses no provider, budget or tier. The shell starts it (`AppUpdateToast` in the app layout), so a release whose music services fail to load still learns that a newer version is out, which is when its users need the fix most.

```sh
scripts/run.sh pnpm vitest run apps/web/src/app/services                # unit and tier tests
scripts/run.sh pnpm --filter @fxm/web exec playwright test playback      # in Chromium (FXM_E2E_PORT to move it off 4173)
```
