# Matching evaluation (stage 1.12)

The matching engine decides whether a match plays without asking (the **Auto** band) or only after the user picks it (**Suggest**). A wrong Auto play is the worst thing the matcher can do, so FXM ships the Auto band only behind a switch, the **matching config**, and turns it on only when an evaluation on held-out tracks shows that it is safe ([PLAN.md 1.12](../../../../../docs/PLAN.md#112-matching-evaluation-labelled-set-report-and-auto-switch), [ARCHITECTURE.md §12](../../../../../docs/ARCHITECTURE.md#12-matching-engine-packagescoresrcmatching)).

This folder holds that evaluation: the labelled set, the offline replay, the label rules, the calibration, the report and the config. The recorder that fetches the pages lives in [`@fxm/sources/eval`](../../../../sources/src/eval/README.md), so `@fxm/core` stays free of network code.

**Today the Auto band is off, and M1 is Suggest-only.** The committed set is the recorder's proof run (8 tracks); the full set (about 370 tracks) is recorded with the commands in [the recorder's README](../../../../sources/src/eval/README.md#recording-the-full-set), and even when its report passes, Auto stays off until the owner has finished the review of the labels (`REVIEW.csv`).

## Files

| Path | What |
|---|---|
| `fixtures/groups/*.json` | The labelled set: one file per track ("group") with its inputs, the YouTube Music pages recorded for them, and the labels |
| `REPORT.md` | The report, generated from the set by `eval.test.ts`; CI fails when it is out of date |
| `REVIEW.csv` | The owner's review checklist, generated by the recorder's `label` command; CI fails when it no longer matches the labels |
| `config.ts` | `MATCHING_CONFIG`: the Auto switch and the tuned thresholds, exported from `@fxm/core` |
| `types.ts`, `recording.ts`, `replay.ts` | The set's data model and its checks, how pages are filed and answered, and the offline replay |
| `labels.ts`, `categories.ts` | The label rules and the review checklist; splits and categories |
| `evaluate.ts`, `tune.ts`, `report.ts` | One case's outcome; the calibration; the report and the gate |

The tooling is exported from `@fxm/core` as the `matchingEval` namespace (for the recorder and tests); the app only needs `MATCHING_CONFIG`, `isAutoMatchAvailable` and `matchingOptions`.

## The labelled set

A **group** is one recording to find: a Spotify track (`sp:<id>`), a row of the owner's CSV (`csv:<id>`), or an input written down from research (`fx:<name>`). Each group has one **input** per slice, and each input is one **case** of the report:

| Slice | What the matcher gets |
|---|---|
| `spotify` | Spotify's metadata as the app has it (stage 1.5): the title with Spotify's suffixes, artists, album, duration, explicit mark, and the ISRC, label, release date and album type from `metadata/4` |
| `csv` | A row of an Exportify-style CSV the owner exported |
| `fixed` | An input from earlier research: the two known ISRC squatters |
| `data-export` | A row of Spotify's "Download your data" export: the title, the main artist only (the export names one artist per stream, "Name of the artist, band or podcast" in Spotify's description of it), the album and the track URI. As imports do, MusicBrainz's exact path fills in the ISRC and the recording's length when it can; otherwise the match runs in no-duration mode (Suggest at most). Made from the Spotify rows by dropping what the export lacks |
| `musicbrainz-exact` | The recording MusicBrainz links to the Spotify track, with its own title, credits, length and ISRCs |
| `musicbrainz-fuzzy` | Spotify's names, duration and explicit mark with the ISRC of a MusicBrainz recording search, which is only a ranking hint: the case of full metadata without a trusted ISRC, where only text can make a match play without asking |

The slices that do not use Spotify's metadata are `data-export` (the export's names, filled in by MusicBrainz) and `musicbrainz-exact`.

Every group has a **split**, `held-out` or `calibration`, from a hash of its ID (30 % calibration), so no group can move after it has been seen. Thresholds are tuned on the calibration split only; the Auto gate reads the held-out split only.

**Categories** (a case can be in several): `mainstream` (popularity 50 or more, not classical or a Spotify Single), `long-tail` (popularity 30 or less), `regional` (a national chart, or a title or artist in a non-Latin script), `cross-script` (YouTube Music titles the recording in another script than the input: an item labelled `exact` or `equivalent` whose title shares no script with the input's), `classical`, `re-recording` ("Taylor's Version", "Re-Recorded"…), `compilation`, `spotify-singles`, `isrc-squatter` (the known inputs whose ISRC another catalogue gives to another recording, `FIXED_INPUTS`) and `data-export` (the data-export rows, and only them). Groups store the categories of their inputs; `cross-script` follows from the labels alone, so it is never stored. The matcher's own decisions never decide a category. An ISRC search that leads with another recording (filler when YouTube Music lacks the ISRC) is not a squatter: the ISRC tables count it in their own column.

**The recording.** For each input, the recorder runs the matching planner exactly as `runMatch` does live, with each option set of `RECORDING_OPTIONS` (the defaults, the measured fallback, and the strictest corner of the calibration grid), once as it is and once with the ISRC-miss cap lifted, and records every page any of them asks for. Pages are filed by key and shared within a group:

| Key | Page |
|---|---|
| `isrc-songs/<attempt>/<ISRC>` | The songs search for the ISRC (attempt 2 is the retry, which YouTube Music answers differently at times) |
| `isrc-top-card/<ISRC>` | The unfiltered search's top-result card (`null` when it is not a track) |
| `songs/<query>` | A songs search: the text search, or the one with the album |
| `description/<videoId>` | A video's release facts ("Provided to YouTube by", ℗ label, release year) and the lines YouTube generated, for people |
| `videos/<query>`, `youtube/<query>` | Music + Video mode's searches (not recorded so far: the report covers Music mode) |

Items keep what the engine reads (kind, title, artists, album and its browse ID, duration, explicit badge, release date, song link). A page YouTube says it does not have is filed as `{ "error": "NotFound" }`, and the replay skips it as the live match would; any other failure leaves the page unrecorded for the next run. `parseEvalGroup` checks every field of a group file, so a hand edit that breaks one fails the replay with the field's path.

## Labels

Each candidate the report reads (every input's pick, with and without the ISRC cap, and the first item of each ISRC search) gets a label: `exact` (the same recording on any release, a remaster or compilation included), `equivalent` (the same audio in another form) or `wrong` (another recording, version, edit, master, song or artist).

**The rules** (`labels.ts`) decide a label only on evidence that does not come from the matcher's score:

- **Certain `wrong`:** a version tag on one side only, two different remixes, a featured artist the input does not credit, more than 10 s apart, explicit against clean, another title, no shared artist.
- **Certain `exact`:** found by an ISRC search for the group's ISRC (Spotify's or MusicBrainz's) with the input's title and artist and within 3 s; or within 3 s with the input's title and artist and a description whose ℗ label or release year agrees; or on the input's own album (not a compilation title or a self-titled album).
- **Anything else is ambiguous:** the rules draft a label (`exact` for the same title, artist and length without such evidence; `wrong` otherwise or when the description names another label two or more years earlier) and mark it `ambiguous`.

**Agents** may draft ambiguous labels with their own evidence (`by: "agent"`); the rules never overwrite an agent's or the owner's label.

**The owner** reviews every ambiguous label and a fixed 10 % sample of the certain ones in `REVIEW.csv`: open each link, listen, and write in `decision` the label (`exact`, `equivalent` or `wrong`) or `ok`, which confirms the draft the row shows. The recorder's `apply-review` command writes the decisions back (`by: "owner"`, with the draft they replaced or confirmed in `draft`); it refuses an `ok` whose row shows a draft that is no longer the label, so the owner never confirms a label they did not see. A cell that a spreadsheet would read as a formula (a videoId such as `-FosatJWWas`, a title starting with `=`) is written with a leading `'`, and `apply-review` reads it back without it.

**A spot check the owner overturns** shows that the rules' certain labels can be wrong, and most Auto plays rest on them (ISRC hits are certain). From then on the review is complete only once the owner has also checked every certain label a held-out Auto play rests on: the checklist lists them as `auto-play` rows, and the report counts the overturned spot checks.

**The time it takes:** about 3 minutes per ambiguous row and 1.5 minutes per spot check or `auto-play` row. The plan expects 30–50 ambiguous rows; at the proof run's rate (2 of its 8 tracks, about one certain label per track) the full set could give up to about 90, with about 45 spot checks. So plan for 2½ to 5 hours; the report prints the minutes left once the set is recorded.

## The report

`REPORT.md` replays every case with the matching config's settings and the Auto setting on, and shows per category (all ten, also those without a case), per split and per input slice:

- **Auto rate, wrong Auto plays** (and unlabelled ones, which count as wrong for the gate) **and Suggest rate**, with the share of suggestions that are right;
- **MusicBrainz exact-path coverage:** how many Spotify tracks MusicBrainz links to exactly one recording, with one ISRC or several, and whether they include Spotify's;
- **what the ISRC-miss cap costs,** per category (the data-export rows, whose ISRC comes from the exact path, included) and per slice: Auto plays with the cap and with it lifted (a missed trusted ISRC then caps nothing), how many wrong Auto plays it prevents, and how many trusted ISRCs led their songs search with another recording;
- every wrong or unlabelled Auto play, and every case whose replay lacked a page, by name.

**The gate** (`EVAL_GATE`), on the held-out split:

- at least 200 groups;
- at least 150 groups (tracks) with an Auto play: Auto plays count once per track, since a track's inputs replay the same pages and mostly pick the same video, so they are not independent trials;
- no wrong and no unlabelled Auto play, on any input of any track;
- no Auto play whose replay lacked a page (a page recorded as missing can hide a candidate or a release fact that would change the decision);
- at least 85 % Auto on at least 40 mainstream tracks (their main input);
- a calibration that found a setting without a wrong Auto play (see below): no threshold stops an ISRC-verified wrong Auto play, so a calibration without a safe setting keeps Auto off whatever the held-out split shows.

Zero wrong in 150 tracks bounds the wrong-Auto rate per track below 2 % at 95 % confidence (1 − 0.05^(1/n)); the report prints the bound for the actual number of tracks, and the number of Auto plays over every input for information.

**Calibration** (`tune.ts`): no change without evidence. When the research's defaults make no wrong Auto play on the calibration split, they stay. Otherwise the tuner tries a grid of stricter settings (the measured fallback, and higher score, title and margin thresholds), keeps those without a wrong Auto play there, and picks the one with the most mainstream Auto plays, then the most Auto plays, then the fewest changes. When none is safe it falls back to the strictest, and the gate fails.

## The Auto switch

`MATCHING_CONFIG` holds `auto`, the reason, the tuned thresholds, the measured fallback and the matcher version it was evaluated with. The app shows its Auto setting only while `isAutoMatchAvailable()` is true, and matches with `matchingOptions(settings)`, which passes the config's thresholds and fallback, and the user's Auto setting only while the band is available:

```ts
import { effectiveMatchBand, matchingOptions, runMatch } from '@fxm/core'

// A provider's AudioSource.match: the verdict must be decided with the evaluated settings.
const result = await runMatch(track, fetchPage, matchingOptions({ mode: ctx.mode }))

// At play time:
const options = matchingOptions({ autoMatch: settings.autoMatch, mode: settings.mode })
const band = effectiveMatchBand(candidate.verdict, options.auto === true) // 'suggest' while Auto is off
```

`eval.test.ts` keeps the config honest: its thresholds must be the calibration split's choice, and `auto` may be `true` only when the committed report's gate passed and the owner's review is complete. A new matcher version (`MATCHER_VERSION`) turns the band off until the report is made again.

**To turn Auto on:** record the full set, label it, have the owner review `REVIEW.csv` and apply it, regenerate the report (`scripts/run.sh pnpm vitest run packages/core/src/matching/eval -u`), and, if the verdict says Auto may be on, set `auto: true` with a reason that cites the report.

## What the proof run showed (2026-10-25, 8 tracks)

The proof run is too small to judge the matcher, but it already shows cases the full run will measure:

- An ISRC hit can miss the gate's duration window by a hair: YouTube Music's single of Vaundy's "しわあわせ" is the first item of both ISRC searches and the top-result card, but 5.5 s longer than Spotify's album track, outside the window of 5.47 s. The ISRC-miss cap then keeps the right song at Suggest.
- Spotify Singles keep " - Spotify Singles" in their titles, which the matcher reads as part of the title, and their ISRCs return only filler on YouTube Music.
- The data-export rows reach Auto only through MusicBrainz's exact path, which linked 4 of the 8 tracks.
- A data-export row names one artist, which for classical music is the composer: for Lang Lang's recording of Bach's C major prelude, the row "Johann Sebastian Bach" finds another performance, 54 s shorter, which the matcher then suggests.
- Its 10 held-out Auto plays come from 3 tracks, so they bound the wrong-Auto rate only below 63 %.

## Replaying and updating

```sh
scripts/run.sh pnpm vitest run packages/core/src/matching/eval      # replay the set, check the report, the checklist and the config
scripts/run.sh pnpm vitest run packages/core/src/matching/eval -u   # write REPORT.md again after the set or the matcher changed
```

Replaying the full set takes about 1,600 replays (every input with the shipped settings, and the uncapped ones), at 10 to 20 ms each on an idle machine and up to about 120 ms under heavy load: from half a minute to about 3 minutes. When the defaults make a wrong Auto play on the calibration split, the tuner replays that split for each of its 24 settings too, which adds up to about 12,000 replays. Nearly all of the time goes into the engine's text normalization, which it repeats for every planner step.
