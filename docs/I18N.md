# Translations (i18n)

FXM's text is hard-coded English in every app. This document says how FXM translates it: how messages are written, which runtime formats them and what it costs the bundle, where catalogs live and how they load, how each app gets its strings, how the locale is chosen, how numbers and dates are formatted, how copy that depends on release flags stays correct, how tests stay readable, and in which order the apps are converted.

**Status.** Stage 8.5 delivers the foundation: this design, the [`@fxm/i18n`](../packages/i18n/README.md) package (runtime, negotiation, Intl formatting, React hooks, pseudo-locales, catalog checks) and the string inventory (§12). No app imports the package yet. Converting the apps is phase 2 (§13), which waits for the branches that are changing `apps/web` now.

**Measurements** in this document were taken on 2026-10-26 on `develop` at ecaa869: bundle sizes with rolldown 1.2.13 (the bundler of Vite 8.3.4, which builds the app) and brotli at quality 4, the way stage 8.5a's budgets measure; the inventory with the package's own tool.

## 1. Decisions

| Question | Decision | § |
|---|---|---|
| How messages are written | Keyed messages in a subset of ICU MessageFormat: values, `number`/`date`/`time` styles, `plural`, `selectordinal`, `select`, and tags around part of a sentence | 2 |
| Keys | Namespaces drawn along chunk boundaries and declared next to the code that shows them (`defineMessages` in `*.messages.ts`), short camelCase keys; argument types read from the English text | 2 |
| Library | An in-house runtime on the platform's `Intl`: 3,881 bytes of brotli, 4,201 with the React bindings. No new runtime dependency | 3 |
| English | Bundled with the code that uses it: a namespace is imported only by code that loads together, so lazy pages carry their own, and a guard on the build's chunks keeps it so | 2, 4 |
| Other locales | JSON per locale and namespace, loaded as one chunk per locale and app; runtime-cached by the service worker, not precached | 4 |
| Negotiation | The Settings choice, else the browser's languages by language and script, else English; the user's own tag formats numbers and dates | 6 |
| Direction | `lang` and `dir` on `<html>` from the locale; logical CSS properties; catalog data in `dir="auto"` | 6 |
| Formatting | `Intl` only, through the package's helpers | 7 |
| Release-flag copy | Whole-message variants and selects chosen by the flag; lists through `Intl.ListFormat`; no articles, capitals or punctuation built in code | 8 |
| Tests | Keep asserting English; one pseudo-locale pass per converted screen; CI checks every catalog | 9 |
| Pseudo-locales | `en-XA` (accented, about a third longer) and `ar-XB` (right to left), in development and fake builds | 10 |
| Site | Static pages per locale with Astro's i18n routing, rendered at build time, with no client code | 5.3 |
| FXM Connect | The browser's own `_locales`: it follows the browser's language | 5.4 |
| Desktop, Android | The page sends the tray and dialog text to the desktop shell; Android keeps its resources, with the per-app language set from Settings | 5.5, 5.6 |

What there is to translate: **2,495 messages and 18,522 words** today (§12), 2,042 of them in the web app.

## 2. How messages are written

### Syntax

Messages use a subset of [ICU MessageFormat](https://unicode-org.github.io/icu/userguide/format_parse/messages/), the syntax translators and their tools (Weblate, Crowdin, Pontoon) already know and check.

| Write | For |
|---|---|
| `{name}` | A value. Text stays as it is; numbers and dates are formatted for the locale |
| `{n, number}`, `{n, number, integer}`, `{n, number, percent}` | A number |
| `{d, date}`, `{d, time, short}` (`short`, `medium`, `long`, `full`) | A date or a time |
| `{n, plural, =0 {No songs} one {# song} other {# songs}}` | A count: an exact option first, then the locale's plural category from `Intl.PluralRules`, then `other`, which every plural needs. `#` is the number, formatted |
| `{n, selectordinal, one {#st} two {#nd} few {#rd} other {#th}}` | An ordinal |
| `{tier, select, free {Free only} lite {Lite} other {Full}}` | A choice by value |
| `Read the <link>release notes</link>` | Part of a sentence that a renderer wraps, so the sentence stays one message |
| `''`, `'{literal}'` | Quoting, as ICU 4.8 and later do it: an apostrophe quotes only before `{`, `}`, `<` (or `#` in a plural), so "doesn't" needs nothing |

Everything else ICU has is refused with an error, so a message never means something different in FXM than in a translator's tool: `offset:`, number and date skeletons (`::`), `choice`, `spellout`, `duration` and `ordinal` arguments, other styles. None of them is needed today; adding one later is a small change to [`packages/i18n/src/parse.ts`](../packages/i18n/src/parse.ts) and its type-level twin. A self-closing tag (`<br/>`) is plain text, as FormatJS reads it too; since it would show on screen as written, the CI check warns about one in a translation.

Why this subset rather than all of ICU or MessageFormat 2: plurals and selects are what FXM's copy needs (the inventory found counts, flags and kinds everywhere, §12), tags keep its many sentences with links whole, and the rest would cost bytes (§3) that no message uses. MessageFormat 2 is stable since CLDR 47, but its library is twice the size of this runtime and translation tools support it less widely than ICU today.

### Namespaces and keys

A namespace holds the English messages of code that loads together, and is declared next to that code. It is one module, and a bundler puts a module in one chunk; its messages are one object, which no bundler can split by key. So a namespace that a module of the first load imports takes all its messages into the first load, a lazy page's too: one namespace per feature folder would add 1,032 messages of lazy code to the first load today, 16.5 kB of brotli, more than the entry chunk's whole headroom (§3). The rule:

**A namespace module is imported only by modules that load together.** A lazy page may also use the first load's namespaces, which are loaded already; code of the first load never imports a lazy page's.

Most feature folders are one lazy page, and their namespace is the feature's. A folder with code in the first load and a lazy page has two: the durations and dates of `features/library/format.ts` ("under a minute", "just now"), which the first load imports, are `library`, and the library page with its dialogs is `libraryPage`. Of the 22 folders with text in the first load, 17 have lazy code with text too (`first-load` in §3 lists them); `library`, `sync`, `connect`, `localFiles` and `downloads` hold most of it.

```ts
// features/library/library-page.messages.ts
import { defineMessages } from '@fxm/i18n'

export const libraryPageMessages = defineMessages('libraryPage', {
  title: 'Library',
  songCount: '{count, plural, one {# song} other {# songs}}',
  removed: 'Removed “{title}” from <link>{playlist}</link>',
})
```

- **Files:** a namespace lives in `<name>.messages.ts` next to the code that shows it, named after the namespace in kebab case: `features/library/library.messages.ts` declares `library`, `features/library/library-page.messages.ts` declares `libraryPage`. The extract script finds namespaces by that suffix and refuses a name that doesn't match its file. (`features/sync/messages.ts` and `features/local-files/messages.ts` hold copy as functions today; phase 2 converts them like any other code.) A stage that owns a feature folder owns its namespaces, as it owns its code.
- **Namespace:** the module's name in camelCase (`library`, `libraryPage`, `localFiles`, `spotifyAccount`). A message's id in translation files is `<namespace>.<key>`. Words every screen uses (Cancel, Close, Try again, Coming soon) live in a `common` namespace in `apps/web/src/i18n/`; it is in the first load, so it holds only words the first load shows too.
- **The guard.** Stage 8.5a's chunk graph (`chunkGraph` in `apps/web/e2e/budgets/chunks.ts`) fails the budgets when a lazy feature's root lands in the first load, unless its group lists it in `inFirstLoad`. Phase 2's step 0 adds the same for namespaces: every `*.messages.ts` module in the first load, in the entry chunk or a chunk it imports, must be listed in `FIRST_LOAD_NAMESPACES` (`budgets.ts`), and every listed one must be there, so a lazy page's namespace can't join the first load unnoticed and the list only changes on purpose. `first-load` shows the same before a build, from the static imports.
- **Keys:** camelCase words that say what the message is for (`removeFromQueue`, `emptyLiked`), never what it says today or where it sits (`text2`, `buttonLabel`). A key stays when the English is reworded; it changes when the meaning does, which sends the message back to translators.
- **Types:** keys are typed, and so are the values each message takes, read from the English text (`MessageValues` in [`packages/i18n/src/messages.ts`](../packages/i18n/src/messages.ts)): `t('songCount', { count: 3 })` compiles, `t('songCount')`, `t('songCount', { count: '3' })` and `t('songCont')` don't. The types can't drift from the text, and a message whose values change breaks every call site that needs updating.
- **Notes for translators** go in a comment above the message. How they reach translators depends on the translation platform (§14): plain JSON has no room for them, so an export step writes them in the platform's format once one is chosen.

### Writing rules

These follow from what the app does today; phase 2 converts these patterns.

1. **Whole sentences.** Never build a sentence from pieces: word order, case and agreement differ between languages. `` `FXM Connect, the desktop app${soon(RELEASED.desktop)}` `` and `` `Retry ${n} failed` `` become messages with values (§8).
2. **Counts are plurals.** `countLabel(count, 'song')`, `` `${n} songs` `` and `count === 1 ? 'artist' : 'artists'` become plural messages with the number inside, since Polish needs four forms and Arabic six. The CI check refuses a translation that lacks a form its language needs (§9).
3. **Choices are selects or separate messages,** never a word swapped into a sentence: a track's kind, a tier, a release flag (§8).
4. **Lists go through `Intl.ListFormat`** (`formatList`), never `join(', ')` with an `and`: "a, b and c" is "a, b y c" in Spanish and "a、b、c" in Japanese.
5. **No capitals, articles or punctuation built in code.** `charAt(0).toUpperCase()`, `upcoming[0] === 'Android' ? 'an' : 'a'` and a trailing `'.'` added to a message all break in other languages; the message carries them.
6. **Links and emphasis inside a sentence are tags** (`t.rich`), never a sentence split around an element.
7. **Values are data.** Song titles, names, addresses, numbers and dates go in as values; numbers and dates are formatted by the message (`{n, number}`) or the helpers (§7), never with `toLocaleString('en')`.
8. **Packages don't translate.** `packages/*` throw errors with codes (`FxmError`) and English messages for developers and logs; the apps map codes to messages, as `features/connect/explain.ts` and `features/downloads/format.ts` already do.
9. **No messages at module load.** A table of copy built when a module loads (`TIER_INFO`, `TIER_FEATURES`, the `RELEASED`-dependent labels) is English forever. It becomes a function or getters that read the translator when the text is shown, as `TIER_INFO.free.summary` already does for the free sources.

## 3. Runtime and bundle size

### What the app counts

Stage 8.5a set the web app's performance budgets (branch `chore/8.5a-e2e-budgets`, `apps/web/e2e/budgets/budgets.ts`; not merged yet), and reset them at de57e1d to `develop` at ecaa869, which had grown since 8.5a's first baseline. The runtime and the messages of the first screen load with the entry chunk, so its budget is the one that matters:

| Budget | Measured (8.5a's reset baseline) | Budget | Headroom |
|---|---|---|---|
| `entry`: the script `index.html` starts | 138.4 kB (444.7 kB on disk) | 152.5 kB | 14.1 kB |
| `initial`: what loads before the app runs | 333.4 kB | 367.5 kB | 34.1 kB |
| `firstVisit`: a first visit with the service worker | 1,696.4 kB | 1,870 kB | 173.6 kB |
| `lcp` on a mid-range phone over Slow 4G | medians of 5,768, 5,980 and 5,776 ms on three CI runners | 6,600 ms | 0.62 s on the slowest |

### The runtime

[`packages/i18n/tools/size.ts`](../packages/i18n/tools/size.ts) bundles each entry an app imports with rolldown, minified as Vite 8 builds the app, and compresses it as 8.5a's budgets do; `size.test.ts` fails when an entry passes its budget, about 10 % over today's size.

| Entry | Minified | Brotli | Budget |
|---|---|---|---|
| `createI18n`, `defineMessages` and negotiation | 9,420 B | 3,881 B | 4,100 B |
| the same with `I18nProvider`, `useT` and `useLocale` | 10,226 B | 4,201 B | 4,500 B |
| every Intl formatter (`createFormatters`, `useFormat`) | 2,819 B | 1,215 B | 1,300 B |
| the pseudo-locales | 733 B | 600 B | 700 B |

Measured alone (`size` prints these parts too), the message parser is 1,225 bytes with its error messages, the parser and message formatting 2,056, and all of negotiation 845 (524 without `negotiateLocale`, which start-up calls once); the instance (catalogs, fallback, reporting) is the rest of the core. Each formatter is a function of its own (`formatDuration(locale, seconds)`), so a chunk bundles only the ones it calls: `formatDuration` alone is 548 bytes with the number formatter it uses.

### Why not a library

Measured the same way, on the same day, with each library's main entry (versions published before 2026-10-12, the repository's 14-day rule):

| Runtime | Minified | Brotli | What it is |
|---|---|---|---|
| **`@fxm/i18n`** (core and React bindings) | 10,226 B | 4,201 B | ICU subset with tags, typed keys and values, negotiation, fallback chains, reporting |
| `intl-messageformat` 12.1.3 | 33,321 B | 10,079 B | FormatJS's full ICU, without `react-intl`'s React layer; 3 more packages |
| `messageformat` 4.0.0 | 22,879 B | 7,627 B | The reference implementation of MessageFormat 2 |
| `@lingui/core` 6.9.1 | 4,705 B | 2,037 B | Formats messages compiled ahead of time; needs Lingui's macro (a Babel or SWC plugin) and CLI in the build. Installing it pulls 36 more packages (its macro, config loader, `jest-validate`, `chalk`, …) |
| `i18next` 26.4.3 | 43,210 B | 14,243 B | No ICU without a plugin that adds `intl-messageformat`; plus `react-i18next` |
| `rosetta` 1.1.0 | 1,449 B | 696 B | Templates only: no plurals or selects |

The full ICU runtimes cost two to two and a half times the in-house one, and `i18next` more than the entry chunk's whole headroom. Lingui's runtime is half the size because its build step parses the messages instead, but it brings a compiler toolchain into a Vite 8 build that has no Babel step today, and 36 packages for the supply chain to vet. The in-house runtime adds no dependency at all, uses the platform's plural rules and formatters, and does exactly what FXM's copy needs; its tests (221, offline) cover the syntax, the type-level parser, negotiation, formatting in several locales, fallback and the React bindings.

The package's development dependencies are pinned to exact versions the lockfile already had: React 19.3.0, react-dom, their types and happy-dom for the React tests, rolldown 1.2.13 and Node's types 22.20.5 for the size check, and `@astrojs/compiler-rs` 0.5.1 (MIT), which Astro already installs, for the inventory's Astro and HTML parsing. None of them reaches a bundle, so `make dist`'s licence check never sees them; `pnpm install` checked them against the 14-day rule when they entered the lockfile.

### What the first load holds

The first load is `main.tsx` and everything it imports statically: 158 modules today, 71 of them with text in 22 feature folders, holding **495 messages** (13,305 characters). [`packages/i18n/tools/first-load.ts`](../packages/i18n/tools/first-load.ts) finds them from the inventory (§12), with `scripts/run.sh pnpm --filter @fxm/i18n first-load`: it follows the static imports the bundler follows, and on this commit found the same 158 modules that `make dist`'s bundle inventory lists in the entry chunk and the chunks it imports.

**Where namespaces are drawn decides the rest.** With namespaces along chunk boundaries (§2), those 495 messages are what phase 2 puts in the first load, and the guard keeps it so. With one namespace per feature folder, the namespaces that the first load imports would bring their folders' lazy code along: **1,032 more messages** (36,151 characters: `library` 244, `sync` 154, `connect` 146, `localFiles` 122, `downloads` 95, `settings` 71, `home` 65, `nowPlaying` 51, `audioEffects` 39 and 45 in eight more folders), 16,454 bytes of brotli with their keys, more than the entry chunk's 14.1 kB headroom on their own. Compressed inside the entry chunk of `make dist`'s build (measured once, on 8.5a's) instead of alone, their text costs about 2 % less, which changes nothing.

Every message in the first load also costs its id: a key in its namespace and the call that looks it up. `first-load` rebuilds the 495 messages in each shape below, as a minifier writes code, and compresses that against today's inline strings:

| Shape | Added brotli for 495 messages |
|---|---|
| Keyed namespaces with descriptive keys (11.1 characters on average), the design above | 4,469 B |
| Two-word keys (8.8 characters) | 3,920 B |
| Each message an exported constant with a full id (`message('library.title', …)`, `t(m.title)`) | 4,729 B |
| Ids shortened to 5-character hashes by a build step | 4,383 B |
| Keys compiled to positions in per-namespace arrays by a build step | 637 B |

So about 9 bytes per message, whichever ids are used: descriptive keys compress against the English words they come from, and random short ids are pure entropy. Only taking ids out entirely (positions) is much cheaper.

**What phase 2 adds to the first load:** about 4.2 kB of runtime and 4.5 kB of keys, about 8.7 kB of the entry chunk's 14.1 kB headroom if all 495 messages land in it (some land in other initial chunks, whose headroom is larger). That fits, but tightly, and only with lazy pages' messages kept out. The levers, in order of cost:

1. Keep strings out of the first load the way code is kept out: namespaces along chunk boundaries, checked by the guard (§2). This one isn't optional.
2. A build step that compiles keys to positions (the last row: saves about 3.8 kB). Both the English namespaces and each locale's catalog are compiled by the same build, so positions agree; call sites need the translator's namespace resolved at build time, which the `useT(namespace)` convention makes possible.
3. A build step that compiles messages to their parsed form, which drops the parser from the bundle (about 1.2 kB) at the cost of slightly larger catalogs.

Whether phase 2 takes the second or the third, or the entry budget grows instead, is the owner's call (§14). Phase 2 measures the entry chunk after each conversion step either way, with 8.5a's budgets.

## 4. Catalogs: where they live and how they load

### Files

| What | Where | Written by |
|---|---|---|
| English messages | `<name>.messages.ts` next to the code that shows them, one namespace each (§2): `apps/web/src/features/library/library-page.messages.ts`, `apps/web/src/i18n/common.messages.ts`, `apps/web/src/embed/embed.messages.ts` | Developers, with the code |
| English for translation tools | `apps/web/src/locales/en/<namespace>.json` | A script (`pnpm --filter @fxm/web i18n:extract`), from the namespaces; a test fails when it is stale |
| Translations | `apps/web/src/locales/<locale>/<namespace>.json`, a flat object of key to message; `<locale>` is a canonical tag (`pt-BR`, `zh-Hant`), which the extract script checks | Translators |
| A locale's chunk | `apps/web/src/locales/<locale>/index.ts`, importing that locale's files | The same script; a test fails when it is stale |

One file per namespace and locale keeps parallel branches from colliding (they own different namespaces), keeps files small enough to review, and maps onto translation platforms, which handle a component per file mask (`apps/web/src/locales/*/library.json`). The site and FXM Connect follow the same pattern in their own folders (§5).

### Loading

- **English needs no loading.** The namespaces are modules, so each lands in the chunk of the code that imports it: drawn along chunk boundaries (§2), lazy pages carry their own messages, the first load only its own, and the embed only the embed's.
- **Another locale is one chunk.** The app's loader is `import.meta.glob('../locales/*/index.ts')`, which gives one dynamic import per locale: the generated `index.ts` imports every namespace file of that locale statically, so Vite emits one chunk per locale with no chunking rules. The catalog of the whole web app is about **106 kB of JSON, 33 kB of brotli** per locale (2,042 messages, 68,036 characters of English as a proxy; German text often runs 20 to 30 % longer). The site's is about 12 kB, FXM Connect's 3 kB.
- **Before the first render.** `main.tsx` negotiates (§6), then, for a locale other than English, awaits `setLocale` before rendering, so nobody sees English flash and then change. If the catalog doesn't arrive within 3 seconds, the app renders in English and switches when it does. Over Slow 4G the wait is one round trip (562.5 ms in 8.5a's model) and 33 kB (0.18 s at 1.47 Mbit/s), so a first visit in German renders about 0.74 s later than in English. That doesn't fit the LCP budget everywhere: on the slowest of 8.5a's runners, 0.62 s is left (a median of 5,980 ms against 6,600 ms), so a German first visit would land near 6.7 s there. Splitting each locale into a first-load part (the namespaces of the first load, about 5 kB) and the rest would save about 0.15 s, which would bring it just under. Phase 2's step 0 adds a non-English visit to 8.5a's timing budgets and measures it; whether those visits get an LCP budget of their own, or the first render stops waiting for the catalog, is the owner's call (§14).
- **Offline, and every launch after the first.** The service worker precaches `**/*.{html,js,css,svg,png}` (`PRECACHE_PATTERNS` in `apps/web/pwa/options.ts`), which would download every language on every first visit, 33 kB each. Phase 2 names the locale chunks `assets/messages-<locale>-<hash>.js`, adds them to `PRECACHE_IGNORES`, and caches the one in use at run time, cache first, in a cache of its own beside the ffmpeg core's (`CacheFirst`, `expiration: { maxEntries: 3 }`): a chunk's name carries its content hash, so a stored chunk is never stale, and a new build's catalog comes under a new name. English users pay nothing, and a German user's app opens in German from the cache after its first visit, online or not. Network first, as the ffmpeg core is cached, would make every launch in another language wait for the network before its first render: `main.tsx` waits for the catalog (above), and Cloudflare Pages revalidates every file by default (`pwa/host.ts`; nothing marks `/app/assets/*` immutable), so even a stored chunk would cost a round trip, and a poor connection the whole 3 seconds before the app rendered English, while an English launch starts from the precache without the network. Network first stays for files without a version in their name, like the ffmpeg core's `ffmpeg-core.json`.

## 5. How each app gets its strings

### 5.1 The web app

- **One instance.** `apps/web/src/i18n/app-i18n.ts` creates the app's `I18n` with the locales that have catalogs, the glob loader, `onMissing` and `onError` that log in development (and count in Diagnostics), and the pseudo-locales in development and fake builds only.
- **Start-up** (`main.tsx`): read the Settings language, negotiate, `await appI18n.setLocale(choice.locale, choice.formatLocale)` (§4), `applyDocumentLocale(choice)` so `<html lang dir>` are right before React renders anything, then render. A later change in Settings goes through the same steps, and the theme script in `index.html` stays untouched: nothing renders before `main.tsx` sets the attributes, so no inline script needs a new CSP hash.
- **Components** take a translator with `useT(namespace)`; `App` wraps the router in `I18nProvider`. **Code outside components** (tables of copy, toasts, announcements, error explanations) calls `appI18n.translator(namespace)` when the text is shown.
- **Settings → Language:** "System default" (follow the browser) and every locale whose catalog is complete enough to ship (§11), each named in its own language (`autonym('de')` is "Deutsch"). The choice is stored as `language` in the settings store (`fxm.settings.v1`, unknown values falling back to the default), follows other tabs like the theme, and syncs between devices like the theme and the catalog mode (§14 asks the owner).
- **Titles and announcements.** Route handles (`page('Album')`, `tab('Home')`) carry message references, resolved where the title is shown, in the document title and by `RouteAnnouncer`. Live-region text (the reorder announcements, toasts) is messages like any other.
- **Service content language.** YouTube's `hl` and `gl` follow `navigator.language` today (`features/search/queries.ts`), and the YouTube provider reads YouTube's own labels by that language (`labelsFor` in `packages/sources/src/youtube/config.ts`). Whether they follow FXM's language instead, so shelf titles from YouTube Music match the interface, is an owner question (§14); the provider falls back to English labels for a language its config doesn't know, so either is safe.
- **The installed app's manifest** (name, description, shortcuts) stays English: web app manifests have no per-locale fields that browsers widely apply yet.

### 5.2 The embed

The embed is its own entry (`vite.embed.config.ts`) with its own small copy (56 messages). It declares the `embed` namespace (`apps/web/src/embed/embed.messages.ts`, and imports `common`), and its loader globs only its own locale files, so its chunks hold only what the player shows. Its locale comes from a `lang` option in the player's address when it names an available locale (the embedding page may set its own language), else from the visitor's browser languages; it sets `lang` and `dir` on its document like the app. The share dialog leaves `lang` out by default, so each visitor gets their own language.

### 5.3 The site

- **Static pages per locale.** Astro's built-in i18n routing (`i18n` in `astro.config.ts`: `defaultLocale: 'en'`, `locales`, `routing: { prefixDefaultLocale: false }`, which Astro 7.3.8 supports) keeps English at `/` and puts each other locale under `/<locale>/`. Pages render their messages at build time with the same runtime, in Node, so the site ships no client code for it. Every page links its translations with `<link rel="alternate" hreflang>` (and `x-default`), the sitemap lists them, and the footer has a language list.
- **No automatic redirect.** Choosing a language by `Accept-Language` needs code at the edge (Pages Functions), which the no-servers rule excludes, and `_redirects` can't match headers. A redirect would also hide pages from crawlers.
- **A locale ships whole.** The site builds a locale's pages only when its catalog covers every message of the site, so a page never mixes languages. The legal pages (privacy, disclaimer: 82 messages, 2,195 words) are the most expensive and the most sensitive: they either ship translated with a line saying the English version prevails, or stay English with a translated summary (§14).
- **Release flags.** The site's `AVAILABLE`-dependent sentences (`comingSoon`, `platforms` in `src/lib/copy.ts`, the tier texts in `src/lib/tiers.ts`) become messages with selects and formatted lists (§8). `src/lib/build-check.ts` extends its checks to every locale's pages (a `lang` that matches, a canonical per locale).

### 5.4 FXM Connect

FXM Connect's text lives where browsers expect it:

- **`_locales/<locale>/messages.json`**, generated at build time (`scripts/build.ts`) from `apps/extension/src/messages.ts` (English) and `apps/extension/locales/<locale>.json`. The manifest sets `default_locale: 'en'` and reads its name, description and action title as `__MSG_extensionName__` and so on; the build checks every locale's description against Chrome's 132-character limit (`MAX_DESCRIPTION_LENGTH`). Browser locale folders use underscores (`pt_BR`).
- **The options page** keeps its English in `options.html` as the fallback, and `options.ts` fills each element marked `data-i18n="key"` from `browser.i18n.getMessage`. Its status messages (seven of them, the "Saved." confirmations) come from the same file.
- **Its language is the browser's.** Extension pages follow the browser's interface language (`i18n.getUILanguage()`), as users expect from extensions, and FXM Connect can't read the web app's setting. The extension's i18n has no plurals, and none of its 44 messages needs one.
- **Store listings.** `store/listing/<locale>/summary.txt` and `description.md` next to the English ones. AMO's metadata already uses translated fields (`{ 'en-US': … }` in `store/listing.ts`), which grow a key per locale; Edge Partner Center's listings are entered by hand per language.

### 5.5 Desktop (Tauri)

The desktop shell's own text is small: 23 messages in Rust (the tray menu and its tooltip, the "Allow a new server?" dialog and what the page shows when a server is refused, the close-to-tray notices) and the installer's two descriptions. Rust builds the tray before the page loads, so it starts in English; the page then sends the shell's text in the user's language through a new command (`set_shell_text`, beside `set_now_playing`), and again when the language changes. The menu items already change their text at run time (`set_text` for Play and Pause). The messages live in the web app's `desktop` namespace, so translators see one set of files. Installer languages (NSIS and WiX in `tauri.conf.json`) are optional and come last.

### 5.6 Android

The Android shell's own text is already in Android resources: the server approval dialog (`fxm-http/src/main/res/values/strings.xml`, two plurals and two buttons). Each language adds `values-<qualifier>/strings.xml` (Android's qualifiers: `values-de`, `values-pt-rBR`, `values-b+zh+Hant`), written from the web app's `android` namespace by a script; ICU plural forms map one to one onto Android's quantity strings. Setting FXM's language also sets the app's per-app language (`AppCompatDelegate.setApplicationLocales` through a small plugin call; Capacitor's activity is an AppCompat activity), so native dialogs match, and `res/xml/locales_config.xml` lists the languages for Android 13's per-app language settings. The other 105 strings of the Kotlin and Java code are errors the plugins return to the page, for developers.

## 6. Locale negotiation and direction

### Choosing the locale

`negotiateLocale` ([`packages/i18n/src/negotiate.ts`](../packages/i18n/src/negotiate.ts)):

1. **The Settings choice** wins when there is a catalog for it.
2. Otherwise **the browser's languages**, most preferred first (`navigator.languages`, then `navigator.language`), canonicalized. Each is matched by language and script with likely subtags filled in, so `zh-TW` and `zh-HK` get `zh-Hant`, `zh` and `zh-CN` get `zh-Hans`, and `sr-Latn` never gets Cyrillic `sr`. Among catalogs of one language the region decides, the region asked for or else the one likely for the language, whatever the order of the catalogs: `pt-BR` takes `pt-BR`, `pt-PT` takes `pt-PT`, else `pt`, else `pt-BR`; a bare `pt` takes `pt-BR` and `es` takes `es-ES`. A variety that stands for several regions needs CLDR's parent locales on top, so that `es-MX` and `es-AR` take Latin American Spanish (`es-419`) and `pt-AO` and `pt-MZ` European Portuguese (`pt-PT`), in negotiation and in the fallback chain: a table of them costs about 230 bytes of brotli in the first load, so it comes with the first such catalog (§11), not before. The first browser language with a match wins, so `ja, de-AT, fr` gets German.
3. Otherwise **English**.

Pseudo-locales are only ever chosen in Settings: no browser asks for them.

**Two locales, not one.** The *message locale* is a catalog (`en`, `de`); the *format locale* is the user's own tag when it shares the catalog's language and script (`en-IN` formats `12,34,567` with the English messages; Settings German with a browser in `de-AT` formats as Austria does). Numbers, dates and lists use the format locale.

**Fallback.** A message a catalog lacks falls back along the locale's chain, dropping subtags while the script stays the same (`pt-BR` → `pt`; `zh-Hant-TW` → `zh-Hant`, never `zh`), then to English, and is reported once. So does an empty message, which is how translation platforms write the ones nobody has translated yet (Weblate leaves them in unless its "Remove blank strings" add-on is on); `completion` doesn't count them and the CI check refuses them, so the files say what is translated.

### `lang` and `dir`

`applyDocumentLocale` sets `lang` and `dir` on `<html>` (screen readers pick their voice from `lang`). The direction comes from the locale's script (`ar`, `he`, `fa`, `ur`, `ckb`, `yi`, `dv` are right to left), read from a table of the right-to-left scripts rather than `Intl.Locale`'s text info, which Firefox lacks.

### Right-to-left readiness

FXM has no right-to-left language yet, but its layout should not need rework when one comes:

- **Logical properties.** Tailwind 4 has logical utilities for the physical ones FXM uses: `ms-*`/`me-*` for `ml-*`/`mr-*`, `ps-*`/`pe-*`, `start-*`/`end-*`, `text-start`/`text-end`, `border-s`/`border-e`, `rounded-s`/`rounded-e`; `translate-x` takes the `rtl:` variant instead. Today the web app uses **137 physical utilities in 56 files** (`pl` 28, `pr` 20, `ml` 18, `text-left` 17, `mr` 14, `text-right` 13, `left` 11, …) and 6 physical declarations in its CSS, against 10 logical utilities; the site has 14 physical and 10 logical declarations. Phase 2 converts them in one mechanical pass and adds a guard to `make lint`, like the guard for the old domain, so no new physical one lands.
- **What mirrors.** Arrows that mean back and forward (the top bar's history buttons, chevrons in menus and rows) mirror with `rtl:-scale-x-100`. Media transport controls and the seek bar don't: playback reads left to right in right-to-left interfaces too, which is how Material Design's bidirectionality guidance treats media controls.
- **Data in any script.** Song titles, artists and playlist names can be Arabic in an English interface and English in an Arabic one. Elements that show catalog data get `dir="auto"` (or `<bdi>` inside a sentence), so neutral characters around them land on the right side.
- `ar-XB` (§10) shows all of this without knowing Arabic.

## 7. Formatting through Intl

FXM ships no locale data: every browser it supports has `Intl` with CLDR's data. The helpers ([`packages/i18n/src/intl.ts`](../packages/i18n/src/intl.ts)) cache each formatter per locale and options, so they are cheap in render functions, and each takes the format locale first.

| Need | Helper | Replaces today |
|---|---|---|
| Numbers, percentages | `formatNumber`, `formatPercent` | 26 `toLocaleString('en')`-style calls (import counts, kHz, sizes, times) |
| A track's length, the player's position | `formatDuration(locale, s)`: `3:07`, `1:02:03`, with the locale's digits | `formatTime` in `@fxm/player` |
| A total running time | `formatDuration(locale, s, 'short')`: `1 hr 5 min`, `45 min`, `40 sec` | `formatTotalDuration`, `totalDuration` |
| Sizes | `formatBytes`: `512 bytes`, `4.2 MB` (decimal, as the operating systems show them) | `formatBytes` in `features/downloads/format.ts`; English then writes `kB`, as CLDR does, instead of `KB` |
| Dates and times | `formatDate`, `formatTime` | `Intl.DateTimeFormat('en', …)`, `toLocaleDateString('en-GB', …)` |
| Relative times | `formatRelativeTime(locale, -1, 'day')` (`yesterday`), `formatTimeAgo` (`5 minutes ago`, largest unit that fits) | `addedLabel`, `playedLabel` (which count calendar days, then call `formatRelativeTime`) |
| Lists | `formatList(locale, items, 'conjunction' \| 'disjunction' \| 'unit')` | `Intl.ListFormat('en-GB', …)`, `freeSources().and`/`.or` |
| Language names | `languageName(locale, tag)`, `autonym(tag)` | none yet: the language picker |
| Sorting | `compareText(locale, a, b)`: numbers by value, case and accents ignored | `Intl.Collator('en', …)` in the library and local files |

`Intl.DurationFormat` is not used: Node 22, which runs the tests, doesn't have it, and Firefox gained it only in version 136. Durations are built from unit-formatted numbers and a unit list, which gives the same text in the locales the tests check. Plural messages count with `Intl.PluralRules` of the format locale.

## 8. Copy that depends on release flags

Both the site (`AVAILABLE` in `apps/site/src/config.ts`) and the app (`RELEASED` in `apps/web/src/features/connect/config.ts`) change sentences when a feature ships: "(coming soon)" after an app, "A and B are coming soon.", "an Android app" or "a desktop app". In English the code builds these from pieces, which translation can't survive. The rules:

1. **The flag chooses a whole message, or a branch of a select.** Translators see every variant, and the CI check refuses a translation that lacks one of a select's options: that value would get the translation's `other` text, which says something else, or nothing at all where the select ends in `other {}` (the examples below), so the site would lose its sentence.
2. **Lists are formatted, verbs agree through a plural.** The list comes from `formatList`, and the verb from a plural on the number of items.
3. **No article, capital or "(coming soon)" is glued on in code.**
4. **Every flag combination stays tested in English**, as `copy.test.ts` and `tiers.test.ts` test them today; phase 2 keeps those tests and adds `checkCatalog` for the translations.

Worked examples from today's code:

```ts
// Before (features/connect/tiers.ts):
how: `FXM Connect, the desktop app${soon(RELEASED.desktop)} or the Android app${soon(RELEASED.android)}.`

// After: each option is a message, the flag picks it, the locale joins them.
const tiers = defineMessages('tiers', {
  connect: 'FXM Connect',
  desktopApp: 'the desktop app',
  desktopAppSoon: 'the desktop app (coming soon)',
  androidApp: 'the Android app',
  androidAppSoon: 'the Android app (coming soon)',
  fullHow: '{options}.',
})
t('fullHow', {
  options: formatList(formatLocale, [
    t('connect'),
    t(RELEASED.desktop ? 'desktopApp' : 'desktopAppSoon'),
    t(RELEASED.android ? 'androidApp' : 'androidAppSoon'),
  ], 'disjunction'),
})
```

```ts
// Before (apps/site/src/components/Hero.astro): a list, then "app is" or "apps are".
`The ${joinList(apps)} ${apps.length === 1 ? 'app is' : 'apps are'} coming soon.`

// After: two flags give three sentences, and the flags pick one. Each language writes each
// sentence its own way ("Die Desktop- und die Android-App erscheinen bald.").
appsSoon: '{apps, select, both {The desktop and Android apps are coming soon.} desktop {The desktop app is coming soon.} android {The Android app is coming soon.} other {}}'
```

```ts
// Before (comingSoon in apps/site/src/lib/copy.ts): the list starts the sentence, so code
// capitalizes its first letter and picks "is" or "are".
comingSoon(['a home feed made for you', 'converting downloads to FLAC, MP3 and other formats'])

// After: the list follows a colon, so nothing is capitalized by code and no verb agrees with it.
// The items are messages, joined the locale's way.
upcoming: 'Coming soon: {features}.'
t('upcoming', { features: formatList(formatLocale, items.map((item) => t(item))) })
```

```ts
// Before (platforms() in apps/site/src/lib/copy.ts): "with an Android app coming soon" or
// "with a desktop app coming soon", the article chosen by code.
// After: the article belongs to the message.
withApp: '{app, select, android {with an Android app coming soon} desktop {with a desktop app coming soon} other {}}'
```

```ts
// Before (lib/free-sources.ts and features/connect/tiers.ts):
`Free music from ${free.and}, in lossless FLAC where ${free.several ? 'they have' : 'it has'} it`
// After: the list is formatted and the verb agrees through a plural.
freeLossless: 'Free music from {sources}, in lossless FLAC where {count, plural, one {it has} other {they have}} it'
t('freeLossless', { sources: formatList(formatLocale, names), count: names.length })
```

The English wording may change a little in conversion ("Coming soon: …"); that is a copy decision for phase 2's review, which reads the English diff like any copy change.

## 9. Tests

- **Tests keep asserting English.** English is the source locale and bundled, so the web app's 2,089 Testing Library queries in unit tests and 516 in its Playwright specs (`getByRole('button', { name: 'Play' })`) keep reading as they do. The test setup pins the locale to `en`, whatever the machine's language.
- **Missing translations and forgotten values fail tests.** The app's instance in tests uses `strictReporters` from `@fxm/i18n/testing`, which throw.
- **No translated screen keeps hard-coded text.** Each converted screen gets one test in `en-XA` with `findUntranslated`, which lists the text and the attributes people read (`aria-label`, `title`, `alt`, `placeholder`, …) that still read as plain English, ignoring the test's data. The test formats in `UNTRANSLATED_FORMAT_LOCALE` (Egyptian Arabic), whose digits, dates and units have no Latin letters: in `en-XA`'s own English formats, a size or a date shown outside a message (`4.2 MB`, `Oct 26, 2026`) would read as untranslated, and each test would collect ignores that could hide real copy. English glued to a formatted value (`٣ songs`) still shows.
  ```ts
  await appI18n.setLocale('en-XA', UNTRANSLATED_FORMAT_LOCALE)
  renderApp('/library')
  expect(findUntranslated(document.body, { ignore: [track.title, track.artist] })).toEqual([])
  ```
- **CI checks the catalogs.** One test per app runs `checkSource` on every namespace (syntax, English plural forms, key names, duplicates) and `checkCatalog` on every locale (it isn't empty, parses, takes the same values, keeps the tags, has every plural form its language needs and every option of each select; values left out and stale keys are warnings), and fails when the generated English JSON or a locale's `index.ts` is stale.
- **The browser runs.** Phase 2 adds one Playwright pass in `en-XA` over 8.5a's critical flows, with screenshots, to catch truncation, and one in `ar-XB` for the layout; and a non-English visit to the timing budgets (§4).

## 10. Pseudo-locales

[`@fxm/i18n/pseudo`](../packages/i18n/src/pseudo.ts) makes two pseudo-locales from the English messages as they are shown, so they never need a catalog and always cover everything:

- **`en-XA`, accented:** `Settings` reads `⟦Šééţţîîñĝš⟧`. Every Latin letter is accented, vowels are doubled (a typical sentence grows by about a third, as German and Finnish do), and each message is bracketed. Plain English on screen is text that skips the translations; a missing `⟧` is text cut off; values (titles, names) stay as they are.
- **`ar-XB`, right to left:** each message is wrapped in a right-to-left override in a document whose direction is `rtl`, which shows the layout an Arabic or Hebrew user gets and every physical CSS property that doesn't follow it.

The tags are those Android and Chromium use for their own pseudo-locales. They are in development builds and the fake builds the Playwright tests use (`VITE_FXM_FAKES=on`), listed in Settings → Language there; production builds leave them out (600 bytes).

## 11. Adding a language

1. **Check the plural forms** of the language (CLDR; `new Intl.PluralRules(tag).resolvedOptions().pluralCategories`). The CI check enforces them. For a regional variety that stands for several regions (`es-419`, `pt-PT`), first add CLDR's parent locales for its language to `negotiate.ts`, in `negotiateLocale` and `fallbackChain`, so that `es-MX` gets `es-419` and `pt-AO` gets `pt-PT` (§6).
2. **Create the catalog:** copy `apps/web/src/locales/en/` to `apps/web/src/locales/<tag>/` (or start empty: missing messages fall back to English) and translate. Use BCP 47 tags in canonical form, as `Intl.getCanonicalLocales` writes them: `de`, `pt-BR`, `zh-Hant`. The extract script refuses any other folder name (`pt-br`): the instance keeps its locales in that form, and asks the loader for a catalog by it.
3. **List the locale** in the app's locales, run the extract script (it writes the locale's `index.ts`), and run `make check`. The language appears in Settings once its catalog covers the app's common, shell and player namespaces completely and at least 90 % of the rest (`completion` from `@fxm/i18n/check` measures it); until then it can be tested in a development build.
4. **The site:** `apps/site/src/locales/<tag>/`, then add the tag to Astro's `locales` once the site's catalog is complete (§5.3).
5. **FXM Connect:** `apps/extension/locales/<tag>.json`; the build writes `_locales/<tag with underscore>/messages.json`. The store listing goes in `store/listing/<tag>/`.
6. **Android:** the script writes `values-<qualifier>/strings.xml` from the `android` namespace, and the tag joins `locales_config.xml`.
7. **Desktop:** nothing: the page sends the shell's text.
8. **Right-to-left languages:** check the screens in `ar-XB` first (§6).
9. **Review:** a second speaker of the language reads the screens before the language ships, and the pull request shows screenshots of the main screens.

Translators work through a translation platform or pull requests, which is the owner's choice (§14). The words to translate per language, today: about 11,800 for the web app, 5,100 for the site (2,200 of them on the legal pages), 1,300 for FXM Connect (860 of them in the store listing), 250 for the desktop and Android shells.

## 12. Inventory

### How it counts

`scripts/run.sh pnpm --filter @fxm/i18n inventory` ([`packages/i18n/tools/inventory.ts`](../packages/i18n/tools/inventory.ts), rules in [`tools/strings.ts`](../packages/i18n/tools/strings.ts)) parses every shipped source file of the apps: TypeScript and JSX with rolldown's parser, Astro components and HTML with Astro's own compiler (including their `<script>` bodies), Rust, Kotlin and Java with a small lexer that knows comments, char literals and raw strings. It counts what phase 2 turns into one message:

| Category | What counts |
|---|---|
| Text | A run of JSX or HTML text, with the inline elements (`<a>`, `<strong>`, `<Link>`) and `{values}` inside it: "Read the <a>notes</a>, {name}." is one message |
| Attributes | An attribute people read or hear (`aria-label`, `title`, `alt`, `placeholder`, the `content` of a description `<meta>`) or a copy prop of FXM's components (`label`, `description`, `hint`, `noun`, …) |
| Code | A string or template in code that reads as prose (two words or more); single words only where copy is expected: a `label:`-like property, a `*_LABELS` table, a function named `*Label`, a `showStatus()`-like call, a JSX expression, a route title |
| Other | A string already in Android's resources, or a paragraph or list item of the store listing |
| Errors | The message of a thrown `Error` (or a Rust `Err`, a plugin's rejection); counted apart, since most are for developers |

It skips tests, fakes, fixtures, development data, the site's build checks, the invisible sandbox documents, and strings that are clearly code: class lists, URLs, paths, MIME types, CSP, user agents, SVG path data, markup, identifiers, schemas, `console` and DOM API arguments, comparisons, object keys, types and imports. Brand names alone (FXM, YouTube Music, Spotify, Firefox) are not messages.

**Precision**, checked by reading random samples: text 40 of 40 and attributes 40 of 40 were real copy; code 92 of 100. Six of the eight misses were made-up song titles, artists and lyric lines in the site's demo mockups (34 such strings in all, which the site's count includes), one a developer message and one an enum value. Recall is lower in ways that matter less: single words in places the rules don't recognize, and sentences glued from several literals, which count once per literal. Take the numbers as accurate to about 10 %.

## 14. Open questions for the owner

1. **Which languages first, and who translates?** Volunteers, people the owner knows, or machine translation reviewed by a speaker. Each language is about 18,500 words today (§11).
2. **Where translators work:** a translation platform (Hosted Weblate, for one, has a gratis plan for libre projects; check its current terms) that opens pull requests, or plain pull requests to `locales/`.
3. **The first-load budget:** with namespaces along chunk boundaries (§2), phase 2 adds about 8.7 kB to the entry chunk (4.2 kB of runtime, 4.5 kB of keys) of its 14.1 kB headroom. Accept that, raising the `entry` budget when later stages need the room, or have phase 2 build the key-compiling step that saves about 3.8 kB of it (§3). Either way, the namespaces of lazy pages stay out of the first load: one namespace per feature folder would add 16.5 kB, more than the headroom on its own.
4. **First visits in another language:** waiting for the catalog before the first render adds about 0.74 s over Slow 4G, more than the 0.62 s the LCP budget leaves on 8.5a's slowest runner (§4).
